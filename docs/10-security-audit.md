## Критические

### SEC-01 — секреты в слоях Docker-образа

**Где:** `docker/Dockerfile:20`, отсутствует `.dockerignore`.

`Dockerfile` копирует каталог `config/` целиком: `COPY config/ config/`. Файл `config/.env` правильно исключён из Git, но Git-ignore не применяется при сборке Docker. Поэтому при `docker compose ... build` локальный `.env` с ключом подписи, солью IP и bootstrap-паролем root попадает в неизменяемый слой образа. Его можно извлечь из локального cache, экспортированного образа или registry даже после удаления файла из рабочего каталога.

**Последствия:** захват сессий/PIN-cookie при утечке ключа подписи; захват root на свежей базе при утечке bootstrap-учётных данных.

**Как закрыть:**

1. Сразу сменить `OPENCRM_SECRET_KEY`, `OPENCRM_IP_HASH_SALT` и пароль root; считать текущие значения потенциально скомпрометированными, если образ хотя бы раз собирался.
2. Добавить `.dockerignore` с минимум `config/.env`, `data/`, `storage/`, `.venv/`, `node_modules/` и `.git/`.
3. Вместо копирования всего каталога копировать только исходники конфигурации: `config/__init__.py` и `config/settings.py`.
4. Передавать секреты только во время запуска через Docker secrets/менеджер секретов или защищённый `env_file`, но не в build context.
5. Пересобрать образ без cache и удалить/ограничить доступ к старым образам в registry.

**Проверка после исправления:** `docker build --no-cache ...`, затем `docker image save` и поиск имени переменной `OPENCRM_SECRET_KEY` в tar не должны находить файл `.env` или его значения.

### SEC-02 — production принимает известный пароль root по умолчанию

**Где:** `config/settings.py:18`, `config/settings.py:88-89`, `core/services/auth_service.py:154-164`.

У `root_password` есть известное значение по умолчанию, однако `config_errors()` проверяет только пустую строку. Если на чистой базе включить production, задать ключ подписи и соль, но не задать `OPENCRM_ROOT_PASSWORD`, будет создан root с известным паролем. Проверка подтверждена отдельным запуском `Settings`: известное значение не отклоняется.

**Последствия:** удалённый захват root на первой установке с неполной конфигурацией.

**Как закрыть:**

1. Убрать рабочие значения по умолчанию для `root_email` и особенно `root_password`; использовать `None`/пустое значение только как сигнал ошибки.
2. В production требовать явно заданные `OPENCRM_ROOT_EMAIL` и `OPENCRM_ROOT_PASSWORD`; отклонять известное development-значение.
3. Добавить максимальную длину пароля (bcrypt обрабатывает только первые 72 байта) и отдельный тест, что запуск с отсутствующим или development-паролем невозможен.
4. После bootstrap удалить `OPENCRM_ROOT_PASSWORD` из runtime-секретов либо заменить одноразовый bootstrap-механизм на явную административную команду.

## Высокие

### SEC-03 — stored XSS через SVG при выдаче nginx

**Где:** `core/services/media_service.py:77-86`, `docker/nginx/templates/locations.inc`, `web/main.py:32-33`.

SVG допускается к загрузке. Его очистка регулярными выражениями неполна: например, не удаляется некавычечный обработчик события `onload=...`; это подтверждено вызовом `sanitize_svg`. В development защитный CSP для `/media/` добавляет FastAPI, но production nginx отдаёт `/media/` прямо из volume и не устанавливает этот CSP. В результате SVG можно открыть как документ того же origin и выполнить JavaScript.

**Сценарий:** manager загружает подготовленный SVG, получает его URL через API доски и убеждает root открыть URL. Скрипт не прочитает `HttpOnly` session-cookie, но прочитает CSRF-cookie и сможет выполнять API-запросы от имени root; это достаточно для повышения привилегий и изменения данных.

**Как закрыть:**

1. Предпочтительно вовсе не принимать SVG: конвертировать его в растровый формат в изолированном обработчике или разрешать только JPG/PNG/WebP.
2. Если SVG необходим, использовать XML-парсер и строгий allow-list элементов/атрибутов, а не regex; запретить события, URL, `foreignObject`, анимации, стили и внешние ссылки.
3. Независимо от очистки добавить для nginx `/media/` и `/branding/` минимум `Content-Security-Policy: default-src 'none'; sandbox`, `X-Content-Type-Options: nosniff` и запрет листинга каталогов. Ещё надёжнее — отдавать пользовательские файлы с отдельного cookieless origin.
4. Добавить регрессионные тесты для `onload=`, некавычечных атрибутов, entity-обходов `javascript:`, SVG с namespace и прямого ответа nginx.

### SEC-04 — отзыв публичной ссылки не закрывает уже известные URL медиа

**Где:** `web/public/routes.py:215-229`, `core/services/media_service.py:169-194`, `docker/nginx/templates/locations.inc`.

Страница публичной доски выдаёт постоянные URL вида `/media/{work_uid}/...`. Маршрут медиа и nginx не проверяют ни share token, ни PIN-cookie, ни статус доски. Поэтому посетитель, однажды получивший URL файла, может открыть или переслать его после отзыва ссылки, истечения её срока, снятия публикации доски или смены PIN. Случайный `work_uid` снижает риск угадывания, но не отменяет доступ по уже сохранённому URL.

**Последствия:** отзыв ссылки не выполняет ожидаемую функцию прекращения доступа к материалам.

**Как закрыть:**

1. Не публиковать постоянный URL как единственный контроль доступа. Отдавать медиа через авторизованный gateway, который проверяет действительную ссылку/PIN, либо через короткоживущие подписанные URL.
2. В nginx можно применять `auth_request` к media location; при этом проверка должна быть привязана к конкретной доске/ссылке, а не только к наличию cookie.
3. При отзыве, смене PIN и снятии публикации аннулировать все выданные URL: короткий TTL и ключ/версия доступа в подписи обычно проще и безопаснее, чем ротация файлов.
4. Добавить тест: получить media URL, отозвать share, затем убедиться, что этот URL возвращает `401/403/404`.

## Средние

### SEC-05 — rate limit входа и регистрации допускает блокировку пользователей и DoS

**Где:** `core/ratelimit.py`, `web/api/deps.py:15-20`, `core/services/auth_service.py:31-47`, `web/api/routes/auth.py:36-49`.

Лимитер хранится только в памяти процесса и для входа индексируется только email. Любой знает или угадывает email сотрудника — после пяти неверных попыток он заблокирует вход этому сотруднику на 15 минут. Перезапуск процесса сбрасывает лимит, а несколько workers умножают допустимое число попыток. Регистрация вообще не ограничена и запускает дорогой bcrypt-hash; также `201`/`409` раскрывают факт существования email.

**Как закрыть:**

1. ~~Перенести лимиты в Redis или БД с TTL; не хранить их только в памяти процесса.~~
   **Сделано.** Счётчик живёт в Redis (`core/ratelimit.py`), у каждого ключа TTL длиной в
   окно, служба поднимается всегда и профиля не имеет. `OPENCRM_WORKERS>1` требует и
   заданного `OPENCRM_REDIS_URL` — иначе приложение не стартует. Недоступный
   Redis означает отказ (503), а не молчаливый пропуск.
2. Использовать несколько ключей: account + IP и IP с отдельными, разумными порогами. Не позволять одному внешнему IP полностью заблокировать учётную запись для всех.
3. Ограничить регистрацию по IP, добавить CAPTCHA/allow-list или полностью убрать публичную регистрацию, если она не нужна.
4. Возвращать одинаковый ответ на регистрацию существующего и нового адреса; для login делать dummy bcrypt-проверку, когда пользователя нет, чтобы убрать timing-enumeration.
5. Ограничить размер полей email, name и password на уровне Pydantic и явно обрабатывать пароль длиннее 72 байт.

### SEC-06 — исчерпание ресурсов через загрузки и обработку медиа

**Где:** `web/api/routes/boards.py:95-108`, `web/api/routes/clients.py:137-148`, `core/services/media_service.py:91-165`.

Оба upload route сначала делают `await file.read()`, то есть полностью помещают тело запроса в память, и только затем проверяют размер. Параллельные файлы до 200 MB способны исчерпать RAM. Изображения не имеют лимита на пиксели/размеры после распаковки, а видео запускают ffprobe/ffmpeg в `BackgroundTasks` без очереди, лимитов CPU/RAM и контроля числа задач.

**Как закрыть:**

1. Читать файл чанками во временный файл с жёстким счётчиком байтов; отклонять запрос сразу после лимита. Лимит reverse proxy должен совпадать с лимитом приложения.
2. До `Image.load()` ограничивать ширину, высоту и число пикселей; считать `DecompressionBombWarning` ошибкой. Обрабатывать изображения в изолированном процессе с лимитами.
3. Вынести транскодирование в очередь задач с ограниченной concurrency и cgroup/container-лимитами CPU/RAM/времени.
4. Ввести per-user/IP rate limit и квоты на объём/число файлов.

### SEC-07 — смена PIN не инвалидирует старый доступ

**Где:** `core/security/tokens.py:30-43`, `core/services/share_service.py:43-61`, `web/public/routes.py:73-77`.

PIN-cookie содержит только `share_link_id` и подпись. При смене PIN меняется `pin_hash`, но cookie не содержит версию PIN, дату выдачи или срок действия. Поэтому пользователь, уже прошедший проверку, сохраняет доступ до конца browser session; при деактивации и последующей повторной активации этой же ссылки старый cookie снова подходит.

**Как закрыть:**

1. Добавить в `ShareLink` `pin_access_version` и включать его в подписанный cookie; увеличивать версию при смене/снятии PIN, отзыве и повторной активации.
2. Устанавливать короткий `max_age` и проверять TTL при разборе cookie.
3. При регенерации, смене PIN и отзыве удалять cookie в ответе, если запрос пришёл от текущего посетителя; серверная проверка версии всё равно обязательна.

## Требует решения по продуктовой модели

### SEC-08 — отсутствует object-level авторизация между manager

**Где:** практически все CRM route в `web/api/routes/clients.py`, `boards.py`, `shares.py` используют только `require_staff`; поле `Client.manager_id` не используется для проверки доступа.

Любой активный manager может читать, изменять и удалять любого клиента, доску и public share, если знает ID. Для небольшой команды с полностью общими данными это может быть осознанной моделью, тогда проблему нужно зафиксировать в документации и UI. Если `manager_id` означает владельца портфеля или требуется разделение сотрудников/отделов, это IDOR.

**Как закрыть при необходимости изоляции:**

1. Определить явную политику: owner, team, root.
2. Передавать current user в сервисы и добавлять условия ownership/team во все `get`, search, update, delete, shares и media routes.
3. Проверять существование и допустимость `manager_id` при создании/изменении клиента.
4. Добавить тесты, что manager A получает `403` на объекты manager B, включая ID, поиск, share views и вложенные файлы.

## Что проверено и не является найденной проблемой

- Сессии хранятся в БД в виде SHA-256 хеша, токены генерируются криптографически стойко; при смене пароля остальные сессии отзываются.
- Изменяющие API-запросы с session-cookie проходят CSRF double-submit проверку.
- SQL-запросы используют SQLAlchemy-параметризацию; явных SQL-инъекций не найдено.
- React и Jinja2 используют экранирование; найденный `dangerouslySetInnerHTML` применяется к статическому словарю встроенных SVG-иконок, а не к данным пользователя.
- `npm audit --omit=dev` для текущего lock-файла не нашёл известных production-уязвимостей. Python dependency audit не выполнен: `pip-audit` не установлен. В `pyproject.toml` отсутствует lock-файл/верхние границы большинства Python-зависимостей, поэтому его стоит добавить в CI.
- Автотесты проекта: `68 passed`.
