## Критические

### SEC-01 — секреты в слоях Docker-образа

**Где:** `docker/Dockerfile:20`, отсутствует `.dockerignore`.

`Dockerfile` копирует каталог `config/` целиком: `COPY config/ config/`. Файл `config/.env` правильно исключён из Git, но Git-ignore не применяется при сборке Docker. Поэтому при `docker compose ... build` локальный `.env` с ключом подписи, солью IP и bootstrap-паролем root попадает в неизменяемый слой образа. Его можно извлечь из локального cache, экспортированного образа или registry даже после удаления файла из рабочего каталога.

**Последствия:** захват сессий/PIN-cookie при утечке ключа подписи; захват root на свежей базе при утечке bootstrap-учётных данных.

**Как закрыть:**

1. Сразу сменить `OPENCRM_SECRET_KEY`, `OPENCRM_IP_HASH_SALT` и пароль root; считать текущие значения потенциально скомпрометированными, если образ хотя бы раз собирался.
2. Добавить `.dockerignore` с минимум `config/.env`, `data/`, `storage/`, `.venv/`, `node_modules/` и `.git/`.
3. Вместо копирования всего каталога копировать только исходники конфигурации: `config/__init__.py` и `config/settings.py`.
4. Передавать секреты только во время запуска через Docker secrets/менеджер секретов или защищённый `env_file`, но не в build context.
5. Пересобрать образ без cache и удалить/ограничить доступ к старым образам в registry.

**Проверка после исправления:** `docker build --no-cache ...`, затем `docker image save` и поиск имени переменной `OPENCRM_SECRET_KEY` в tar не должны находить файл `.env` или его значения.

### SEC-02 — production принимает известный пароль root по умолчанию

**Где:** `config/settings.py:18`, `config/settings.py:88-89`, `core/services/auth_service.py:154-164`.

У `root_password` есть известное значение по умолчанию, однако `config_errors()` проверяет только пустую строку. Если на чистой базе включить production, задать ключ подписи и соль, но не задать `OPENCRM_ROOT_PASSWORD`, будет создан root с известным паролем. Проверка подтверждена отдельным запуском `Settings`: известное значение не отклоняется.

**Последствия:** удалённый захват root на первой установке с неполной конфигурацией.

**Как закрыть:**

1. Убрать рабочие значения по умолчанию для `root_email` и особенно `root_password`; использовать `None`/пустое значение только как сигнал ошибки.
2. В production требовать явно заданные `OPENCRM_ROOT_EMAIL` и `OPENCRM_ROOT_PASSWORD`; отклонять известное development-значение.
3. Добавить максимальную длину пароля (bcrypt обрабатывает только первые 72 байта) и отдельный тест, что запуск с отсутствующим или development-паролем невозможен.
4. После bootstrap удалить `OPENCRM_ROOT_PASSWORD` из runtime-секретов либо заменить одноразовый bootstrap-механизм на явную административную команду.

## Высокие

### SEC-03 — stored XSS через SVG при выдаче nginx

**Где:** `core/services/media_service.py:77-86`, `docker/nginx/templates/locations.inc`, `web/main.py:32-33`.

SVG допускается к загрузке. Его очистка регулярными выражениями неполна: например, не удаляется некавычечный обработчик события `onload=...`; это подтверждено вызовом `sanitize_svg`. В development защитный CSP для `/media/` добавляет FastAPI, но production nginx отдаёт `/media/` прямо из volume и не устанавливает этот CSP. В результате SVG можно открыть как документ того же origin и выполнить JavaScript.

**Сценарий:** manager загружает подготовленный SVG, получает его URL через API доски и убеждает root открыть URL. Скрипт не прочитает `HttpOnly` session-cookie, но прочитает CSRF-cookie и сможет выполнять API-запросы от имени root; это достаточно для повышения привилегий и изменения данных.

**Как закрыть:**

1. Предпочтительно вовсе не принимать SVG: конвертировать его в растровый формат в изолированном обработчике или разрешать только JPG/PNG/WebP.
2. Если SVG необходим, использовать XML-парсер и строгий allow-list элементов/атрибутов, а не regex; запретить события, URL, `foreignObject`, анимации, стили и внешние ссылки.
3. Независимо от очистки добавить для nginx `/media/` и `/branding/` минимум `Content-Security-Policy: default-src 'none'; sandbox`, `X-Content-Type-Options: nosniff` и запрет листинга каталогов. Ещё надёжнее — отдавать пользовательские файлы с отдельного cookieless origin.
4. Добавить регрессионные тесты для `onload=`, некавычечных атрибутов, entity-обходов `javascript:`, SVG с namespace и прямого ответа nginx.

### SEC-04 — отзыв публичной ссылки не закрывает уже известные URL медиа

**Где:** `web/public/routes.py:215-229`, `core/services/media_service.py:169-194`, `docker/nginx/templates/locations.inc`.

Страница публичной доски выдаёт постоянные URL вида `/media/{work_uid}/...`. Маршрут медиа и nginx не проверяют ни share token, ни PIN-cookie, ни статус доски. Поэтому посетитель, однажды получивший URL файла, может открыть или переслать его после отзыва ссылки, истечения её срока, снятия публикации доски или смены PIN. Случайный `work_uid` снижает риск угадывания, но не отменяет доступ по уже сохранённому URL.

**Последствия:** отзыв ссылки не выполняет ожидаемую функцию прекращения доступа к материалам.

**Как закрыть:**

1. Не публиковать постоянный URL как единственный контроль доступа. Отдавать медиа через авторизованный gateway, который проверяет действительную ссылку/PIN, либо через короткоживущие подписанные URL.
2. В nginx можно применять `auth_request` к media location; при этом проверка должна быть привязана к конкретной доске/ссылке, а не только к наличию cookie.
3. При отзыве, смене PIN и снятии публикации аннулировать все выданные URL: короткий TTL и ключ/версия доступа в подписи обычно проще и безопаснее, чем ротация файлов.
4. Добавить тест: получить media URL, отозвать share, затем убедиться, что этот URL возвращает `401/403/404`.

## Средние

### SEC-05 — rate limit входа и регистрации допускает блокировку пользователей и DoS

**Где:** `core/ratelimit.py`, `web/api/deps.py:15-20`, `core/services/auth_service.py:31-47`, `web/api/routes/auth.py:36-49`.

Лимитер хранится только в памяти процесса и для входа индексируется только email. Любой знает или угадывает email сотрудника — после пяти неверных попыток он заблокирует вход этому сотруднику на 15 минут. Перезапуск процесса сбрасывает лимит, а несколько workers умножают допустимое число попыток. Регистрация вообще не ограничена и запускает дорогой bcrypt-hash; также `201`/`409` раскрывают факт существования email.

**Как закрыть:**

1. ~~Перенести лимиты в Redis или БД с TTL; не хранить их только в памяти процесса.~~
   **Сделано.** Счётчик живёт в Redis (`core/ratelimit.py`), у каждого ключа TTL длиной в
   окно, служба поднимается всегда и профиля не имеет. `OPENCRM_WORKERS>1` требует и
   заданного `OPENCRM_REDIS_URL` — иначе приложение не стартует. Недоступный
   Redis означает отказ (503), а не молчаливый пропуск.
2. Использовать несколько ключей: account + IP и IP с отдельными, разумными порогами. Не позволять одному внешнему IP полностью заблокировать учётную запись для всех.
3. Ограничить регистрацию по IP, добавить CAPTCHA/allow-list или полностью убрать публичную регистрацию, если она не нужна.
4. Возвращать одинаковый ответ на регистрацию существующего и нового адреса; для login делать dummy bcrypt-проверку, когда пользователя нет, чтобы убрать timing-enumeration.
5. Ограничить размер полей email, name и password на уровне Pydantic и явно обрабатывать пароль длиннее 72 байт.

### SEC-06 — исчерпание ресурсов через загрузки и обработку медиа

**Где:** `web/api/routes/boards.py:95-108`, `web/api/routes/clients.py:137-148`, `core/services/media_service.py:91-165`.

Оба upload route сначала делают `await file.read()`, то есть полностью помещают тело запроса в память, и только затем проверяют размер. Параллельные файлы до 200 MB способны исчерпать RAM. Изображения не имеют лимита на пиксели/размеры после распаковки, а видео запускают ffprobe/ffmpeg в `BackgroundTasks` без очереди, лимитов CPU/RAM и контроля числа задач.

**Как закрыть:**

1. Читать файл чанками во временный файл с жёстким счётчиком байтов; отклонять запрос сразу после лимита. Лимит reverse proxy должен совпадать с лимитом приложения.
2. До `Image.load()` ограничивать ширину, высоту и число пикселей; считать `DecompressionBombWarning` ошибкой. Обрабатывать изображения в изолированном процессе с лимитами.
3. Вынести транскодирование в очередь задач с ограниченной concurrency и cgroup/container-лимитами CPU/RAM/времени.
4. Ввести per-user/IP rate limit и квоты на объём/число файлов.

### SEC-07 — смена PIN не инвалидирует старый доступ

**Где:** `core/security/tokens.py:30-43`, `core/services/share_service.py:43-61`, `web/public/routes.py:73-77`.

PIN-cookie содержит только `share_link_id` и подпись. При смене PIN меняется `pin_hash`, но cookie не содержит версию PIN, дату выдачи или срок действия. Поэтому пользователь, уже прошедший проверку, сохраняет доступ до конца browser session; при деактивации и последующей повторной активации этой же ссылки старый cookie снова подходит.

**Как закрыть:**

1. Добавить в `ShareLink` `pin_access_version` и включать его в подписанный cookie; увеличивать версию при смене/снятии PIN, отзыве и повторной активации.
2. Устанавливать короткий `max_age` и проверять TTL при разборе cookie.
3. При регенерации, смене PIN и отзыве удалять cookie в ответе, если запрос пришёл от текущего посетителя; серверная проверка версии всё равно обязательна.

## Требует решения по продуктовой модели

### SEC-08 — отсутствует object-level авторизация между manager

**Где:** практически все CRM route в `web/api/routes/clients.py`, `boards.py`, `shares.py` используют только `require_staff`; поле `Client.manager_id` не используется для проверки доступа.

Любой активный manager может читать, изменять и удалять любого клиента, доску и public share, если знает ID. Для небольшой команды с полностью общими данными это может быть осознанной моделью, тогда проблему нужно зафиксировать в документации и UI. Если `manager_id` означает владельца портфеля или требуется разделение сотрудников/отделов, это IDOR.

**Как закрыть при необходимости изоляции:**

1. Определить явную политику: owner, team, root.
2. Передавать current user в сервисы и добавлять условия ownership/team во все `get`, search, update, delete, shares и media routes.
3. Проверять существование и допустимость `manager_id` при создании/изменении клиента.
4. Добавить тесты, что manager A получает `403` на объекты manager B, включая ID, поиск, share views и вложенные файлы.

## SEC-09 — выключенный блок `boards` не закрывает публичную витрину

**Где:** `web/public/routes.py`, обработчики `showcase`, `check_pin`, `showcase_data`,
`media_file`.

Правило продукта: выключенный блок исчезает целиком — меню, API, настройки, отчёты
(`CLAUDE.md`, [11-modules.md](11-modules.md)). Страница состояния заказа это правило
соблюдает: `/d/<номер>` первым делом спрашивает `modules_service.is_enabled(db, "documents")`
и при выключенном блоке отвечает так же, как на несуществующий номер. Витрина досок не
спрашивает ничего: `boards` выключается в настройках, раздел пропадает из меню, API
`/api/v1/boards` отвечает `module_disabled` — а выданные клиентам ссылки
`/b/<токен>`, `/b/<токен>/data` и файлы `/media/<uid>/<файл>` продолжают отдавать работы
всему интернету.

**Последствия:** владелец, выключивший блок (сменил род занятий, закрыл направление),
считает, что закрыл его; публичные ссылки при этом живы, и узнать об этом неоткуда.

**Как закрыть** — тем же приёмом, что у бланков, в четырёх обработчиках:

```python
from core.services import modules_service
...
if not modules_service.is_enabled(db, "boards"):
    return _closed_page(request, db)          # у /media/ — JSON 404, как рядом
```

Сторож дописывается в `tests/test_public_surface.py`, в
`test_publichnye_puti_perechisleny_vmeste_s_ikh_blokom`: словарь `trebuetsya` дополняется
строкой `"boards": "/b/{token}"`. Раньше починки его добавлять нельзя — красный сторож
без починки останавливает автообновление боевого сервера.

## SEC-10 — cookie сессии Grafana идёт без флага `Secure`

**Где:** `docker/docker-compose.yml`, служба `grafana`.

Снято с живого стенда, вход верным паролем:

```
set-cookie: grafana_session=…; Path=/monitoring; Max-Age=2592000; HttpOnly; SameSite=Lax
```

`HttpOnly` и `SameSite` на месте, `Secure` — нет: у Grafana `cookie_secure` по умолчанию
`false`, а в compose он не задан. Значит первый же запрос браузера по `http://<домен>/…`
(опечатка, старая закладка, ссылка из письма) увозит cookie сессии панели открытым
текстом — до того, как сработает редирект на HTTPS. HSTS это прикрывает, но только после
первого визита по HTTPS; до него — нет.

**Как закрыть:** одна строка в описании службы `grafana`:

```yaml
      GF_SECURITY_COOKIE_SECURE: "true"
```

Оговорка, без которой правка опаснее болезни: с этим флагом панель перестаёт работать по
обычному HTTP. Установка в локальной сети без домена ходит в Grafana не через `/monitoring/`,
а по `127.0.0.1:9080` (см. `OPENCRM_GRAFANA_BIND`), и туда флаг тоже дотянется. Поэтому
значение стоит брать из окружения — `${OPENCRM_GRAFANA_COOKIE_SECURE:-false}` — и ставить
в `true` там же, где `./opencrm.sh` уже пишет `OPENCRM_MONITOR_URL` со схемой `https://`.

|---|---|---|---|
| CVE-2025-3260 | 8.3 высокая | обход прав на дашборды через новые ручки `/apis` | 11.5.3+security-01 |
| CVE-2025-2703 | 6.8 средняя | DOM XSS во встроенном плагине XY chart | 11.5.3+security-01 |
| CVE-2025-3454 | 5.0 средняя | обход авторизации в прокси источников данных | 11.5.3+security-01 |
| CVE-2025-4123 | 7.6 высокая | XSS + full-read SSRF через client path traversal и открытый редирект | 11.5.4+security-01 |
| CVE-2025-6023 | высокая | XSS, неполная починка предыдущей; ведёт к захвату учётной записи | 11.5.6+security-01 |
| CVE-2025-6197 | средняя | открытый редирект при переключении организаций | 11.5.6+security-01 |

CVE-2025-4123 и CVE-2025-6023 требуют, чтобы жертва перешла по ссылке, будучи
авторизованной хотя бы как Viewer. Для этой установки жертва ровно одна — владелец, он же
администратор Grafana, и его сессия живёт 30 суток. Анонимный доступ выключен, поэтому
без авторизованной жертвы обе не срабатывают.

**Важное про 2026 год:** ветка 11.5 больше не получает исправлений вовсе. Августовские
CVE-2026-27876 (критическая RCE через `sqlExpressions`) и CVE-2026-27880 закрыты в 11.6.14
и 12.x; 11.5 в списке затронутых нет — то есть конкретно этой критической дыры на 11.5.2
не существует, но следующая такая же останется незакрытой навсегда.

**Что предлагается** (правка чужая, сам не менял):

1. Ближайший безопасный шаг без смены ветки — `11.5.6+security-01`. Тег в реестре пишется
   без плюса; перед правкой обязательно проверить, что он существует:
   `docker manifest inspect grafana/grafana:11.5.6-security-01`.
2. Правильный шаг — уйти на поддерживаемую ветку (11.6.14 и выше либо 12.x). Цена: у
   Grafana между минорными версиями меняется схема своей базы, и **откат назад не
   поддерживается**. То есть перед сменой нужна копия каталога
   `${OPENCRM_HOME}/monitoring/grafana`, а не только «если что, вернём тег».
3. Заодно — включить собственную CSP Grafana (`GF_SECURITY_CONTENT_SECURITY_POLICY: "true"`).
   Сейчас панель отдаётся вообще без `Content-Security-Policy` (проверено на стенде), а
   обе высокие CVE — это XSS. Проверять после включения обязательно живьём: у Grafana
   штатный шаблон политики, но сторонние плагины он ломает.

## SEC-12 — заголовки уровня `server` не доезжали до половины ответов

**Где:** `docker/nginx/templates/locations.inc`, `https.conf.template`, `http.conf.template`.

`add_header` в nginx **не наследуется**, если на текущем уровне есть хоть один свой: не
«добавляется к унаследованным», а отменяет их целиком. Снято запросами с живого стенда до
правки:

```
/monitoring/          HSTS есть, Referrer-Policy есть   (своих add_header нет)
/branding/logo.svg    HSTS НЕТ,  Referrer-Policy НЕТ    (есть свой add_header)
/avatars/*.webp       HSTS НЕТ,  Referrer-Policy НЕТ    (есть свой add_header)
страница обслуживания HSTS НЕТ,  Referrer-Policy НЕТ    (есть свой add_header)
```

Меньше всего защиты оказалось ровно там, где отдаётся пользовательский файл, в том числе
SVG. Прочитать это в конфиге было нельзя: строки написаны уровнем выше и выглядят
действующими.

**Закрыто:** набор из трёх заголовков вынесен в `docker/nginx/templates/headers.inc` и
подключается include'ом и на уровне `server`, и в каждый блок со своим `add_header`. HSTS
приезжает переменной `$opencrm_hsts` (`map` по `$scheme` в `hardening.inc`): по обычному
HTTP значение пустое, а `add_header` с пустым значением nginx не выводит — это и позволяет
держать один файл на оба шаблона. Проверено на живом стенде: после правки HSTS и
`Referrer-Policy` есть ровно по одному экземпляру на всех шести проверенных путях, а по
HTTP HSTS не отдаётся.

Сторожа: `test_u_kazhdogo_bloka_so_svoim_zagolovkom_stoit_obshchiy_nabor`,
`test_v_bloke_paneli_monitoringa_net_svoikh_zagolovkov`,
`test_nabor_zagolovkov_zhivet_v_odnom_meste`, `test_hsts_privyazan_k_skheme_a_ne_k_shablonu`.

## SEC-13 — ни у панели, ни у входов в CRM не было ограничителя потока

**Где:** `docker/nginx/templates/locations.inc`, `core/services/auth_service.py:login`.

Замерено на стенде: сорок попыток входа в Grafana — 0.2 секунды, сорок попыток HTTP Basic
на `/monitoring/api/org` — 0.1 секунды, все 401 и ни одного препятствия. У самой Grafana
защиты от подбора нет по устройству.

У CRM ограничитель есть, но считает он **по адресу почты** (5 промахов на учётную запись
за 15 минут). Поток с одного места он не ограничивает вовсе. А `POST /api/v1/auth/register`
(«Запросить доступ», открыт в интернет) не ограничен ничем: каждый запрос с новым адресом
считает bcrypt cost 12 и добавляет строку в `users`.

**Закрыто** ограничителями nginx (`hardening.inc`): 12/мин на `= /monitoring/login`,
12/мин на запросы с `Authorization: Basic` под `/monitoring/`, 30/мин на
`= /api/v1/auth/login`, 6/мин на `= /api/v1/auth/register`. Отказ — 429. Числа, замеры и
довод «владелец не должен заметить» — в шапке `hardening.inc` и в
[07-security.md](07-security.md).

## SEC-14 — `/api/v1/metrics/` со слэшем уходил в приложение

`location = /api/v1/metrics { deny all; }` — точное совпадение, и `/api/v1/metrics/` ему
не равен. Проверено на живом nginx: `//api/v1/metrics`, `/api/v1/./metrics`,
`/api/v1/foo/../metrics`, `%2f` и строка запроса упирались в запрет (nginx приводит их к
тому же пути до выбора блока), а хвост со слэшем — уходил в приложение. Утечки не было по
случайности: Starlette отвечал на него перенаправлением обратно на запрещённый адрес. Но
`redirect_slashes` — настройка фреймворка, а не решение проекта.

**Закрыто:** рядом с точным совпадением добавлен `location ^~ /api/v1/metrics { deny all; }`.
Проверено запросами: все восемь написаний отвечают 403. Сторож —
`test_metriki_zakryty_i_tochnym_sovpadeniem_i_prefiksom`.

## SEC-15 — логотип и аватар вставляются рамкой в чужую страницу

`default-src 'none'` рамку не закрывает: у `frame-ancestors` отката к `default-src` нет по
устройству CSP, а `sandbox` глушит скрипт внутри файла, но не запрещает файлу оказаться в
чужой рамке. **Закрыто:** в политику `/branding/` и `/avatars/` добавлен
`frame-ancestors 'none'`. Сторож — `test_kartinki_nelzya_vstavit_v_chuzhuyu_stranitsu`.

Тот же пробел остался у `/media/` и `/static/`: их политику ставит приложение
(`CSP_MEDIA` в `web/middleware.py`), и `frame-ancestors` там нет. Правка за границей этой
работы; строка та же.

## SEC-16 — `/monitoring/api/health` называет анониму версию Grafana

Единственное, что панель отдаёт без входа: точная версия и хэш сборки. Для сканера это
готовое сопоставление с таблицей CVE. Закрывать не стал намеренно: выигрыш здесь только в
незаметности, а `deny` на этой ручке — та самая правка, после которой чужая диагностика
однажды перестанет работать без объяснения. Правильный ответ на эту находку — SEC-11,
свежая версия.

## Что проверено и проблемой не является

- Анонимный доступ к Grafana закрыт по-настоящему: `/monitoring/api/frontend/settings`,
  `/api/search`, `/api/org`, `/api/datasources`, `/api/admin/settings`, `/api/live/ws` —
  все 401. Страница `/monitoring/signup` рисуется, но `POST /api/user/signup` отвечает 401.
- `X-Frame-Options` на панели ровно один (`deny`, ставит сама Grafana); nginx своего не
  добавляет, задвоения нет. `X-Content-Type-Options` приходит дважды — от nginx и от
  Grafana, значение одинаковое (`nosniff`), поведение браузера от этого не меняется.
- Дашборды и шаблон источников данных секретов не содержат: ни паролей, ни адресов, ни
  внутренних имён. Внутренние адреса источников (`http://prometheus:9090`,
  `http://loki:3100`) видны только вошедшему.
- `/api/docs`, `/api/openapi.json`, `/redoc` в `OPENCRM_ENV=production` не заводятся вовсе.
- Каталоги `/static/` и `/assets/` списка файлов не отдают.
- Cookie сессии CRM и пропуска по PIN: `HttpOnly`, `SameSite=Lax`, `Secure` по схеме
  `base_url`. У cookie CSRF `HttpOnly` нет намеренно — её читает фронтенд.
- Перебор токена публичной ссылки закрыт: 128 бит, а отозванная ссылка и выдуманный токен
  отвечают побайтово одинаково.
- `--no-proxy-headers` у uvicorn на месте; определение адреса клиента целиком за
  `client_ip`.
- `/healthz` отвечает всему интернету — намеренно: по публичному адресу его опрашивает
  blackbox из стека мониторинга.

## Чего проверить не удалось

- Обновление Grafana до предложенной версии: у контейнеров на этом стенде нет выхода в
  сеть, вытянуть другой образ нельзя. Существование тега `11.5.6-security-01` в реестре
  **не проверено** — перед правкой обязательно `docker manifest inspect`.
- Поведение `GF_SECURITY_COOKIE_SECURE` и `GF_SECURITY_CONTENT_SECURITY_POLICY` на живой
  панели: правка в `docker-compose.yml`, файл за границей этой работы.
- Настоящий сертификат и настоящий домен: стенд поднят на самоподписанном сертификате для
  `stand.local`. На поведение заголовков и ограничителей это не влияет, на цепочку доверия
  — влияет, и её проверял мониторинг (`probe_ssl_earliest_cert_expiry`), а не этот разбор.
