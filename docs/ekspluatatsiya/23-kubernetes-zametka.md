# 23 — Переезд в Kubernetes: заметка, не план

Записано 06.09.2026 по просьбе владельца. Это разбор «что будет, если», а не
обещание переезда: решение не принято, и может не быть принято вовсе. Заметка
лежит здесь, чтобы разбор не потерялся, и описывает систему такой, какая она
есть, — с указанием, что именно в ней мешает подам и чем это лечится.

## 1. Вывод

Поднять OpenCRM подами можно, и большая часть работы уже сделана раньше — при
переходе на несколько рабочих процессов ([08](08-razvyortyvanie.md), «Несколько
рабочих процессов») закрыли ровно те беды, что мешают нескольким подам:

- сессии лежат в базе (`user_sessions`), а не в памяти процесса;
- счётчики попыток входа и PIN — в Redis (`core/ratelimit.py`), место разжатия
  картинок — там же;
- живой слой идёт потоком Redis с догоном по номеру записи
  ([12](../ustroystvo/12-zhivye-obnovleniya.md) §5–6); липкие сессии не нужны;
- посев умолчаний при старте — под `redis_client.startup_lock`, работа со
  схемой — под именованным замком MySQL `schema_check.zamok_shemy`;
- инварианты «ровно один» держатся замками строк и `GET_LOCK` — они серверные и
  общие для всех подов;
- кэши в памяти процесса (состав блоков, режим техработ, размер хранилища)
  сходятся сами за секунды и разобраны поимённо в [08](08-razvyortyvanie.md), «Что
  осталось в памяти процесса и почему».

Два пода приложения за Ingress заработают почти без правок кода.
Отказоустойчивость при этом упирается не в приложение, а в три вещи вокруг
него: единственную MySQL, локальный диск с файлами и docker-compose, на который
завязаны обновление, nginx и таймеры.

## 2. Что мешает и чем лечится

### Файлы на локальном диске

`storage/` (медиа досок, файлы клиентов, брендинг, аватары, копии) и `data/`
(дампы перед миграциями) лежат в домашнем каталоге установщика
([08](08-razvyortyvanie.md), «Где лежит состояние»). Замок копий — файловый
(`backup_service`, `O_CREAT|O_EXCL`).

Лечится томом с режимом ReadWriteMany: CephFS, Longhorn RWX или NFS. Замок через
`O_CREAT|O_EXCL` на таких томах атомарен. NFS с одним сервером сам становится
точкой отказа, поэтому для «без отказа» нужен распределённый том. Дальний
вариант — объектное хранилище S3, но это заметная правка `storage_service`,
медиа и копий: слоя абстракции над файлами сейчас нет.

### Медиа раздаёт nginx, а не приложение

`/media/`, `/branding/`, `/avatars/` идут через `alias` на `/srv/storage`
(`docker/nginx/templates/locations.inc`); у FastAPI смонтированы только
`/assets` и `/static`. Лечится либо nginx как sidecar в поде приложения с тем
же томом, либо небольшой правкой `web/main.py` — монтированием этих каталогов
через `StaticFiles` за флагом. Страница техработ у приложения своя
(`web/middleware.py`), здесь nginx не нужен.

### MySQL одна

Код требует одного primary: `SELECT … FOR UPDATE`, именованные замки `GET_LOCK`
(`schema_check.zamok_shemy`, `leads.zapert_priyom`). Multi-primary запрещён по
построению — дуэли из `tests/test_odin_iz_mnogih.py` держатся на замках строк.

Лечится оператором с одним primary и автопереключением (MySQL Operator с
InnoDB Cluster в single-primary, Percona XtraDB Operator) либо управляемой базой
облака. Переключение занимает секунды; на это время сайт отвечает `500`, как и
сейчас при `docker restart db` ([08](08-razvyortyvanie.md), «А что делает система,
когда не отвечает база»).

### Redis без сохранения

Он таким задуман: `--save ""`, `allkeys-lru`, 64 МБ. Потеря даёт `resync`
живого слоя и сброс счётчиков попыток. При лежащем Redis ограничитель уходит в
память процесса, и с несколькими подами порог защиты от подбора вырастает в
число подов — поэтому Redis нужен с Sentinel или как управляемый. В боевом
режиме приложение без адреса Redis не стартует (`config/settings.py`,
`config_errors`).

### Обновлятор и `opencrm.sh` завязаны на compose

`deploy/updater.py` собирает образ, делает `up -d --build`, снимает дамп перед
обновлением, проверяет `/healthz` и откатывает. В кластере это заменяется на
сборку образа в CI, rolling update Deployment с readiness probe и Job миграции.

Миграции в `docker/entrypoint.sh` идут под `zamok_shemy`, N подов друг другу не
мешают, но дамп перед миграцией пишется в `/app/data` — ему нужен том. Откат
базы остаётся ручным. Старые поды во время раската переживают лишние колонки
(`schema_check`: лишнее — только запись в лог), поэтому миграции обязаны
оставаться добавочными — а это уже правило проекта (`CLAUDE.md` §1).

### Таймеры systemd

Копия 03:30, сводка 09:00, уборка телеграма 04:30 (`deploy/systemd/`),
продление сертификата — контейнер certbot. Лечится CronJob с тем же образом:
`python -m scripts.svodka`, `python -m scripts.telegram_uborka`, копия через
`scripts.snapshot_db` на общий том или в S3. Сертификаты забирает cert-manager.

### Ingress и живой слой

SSE на `/api/v1/live` требует отключить буферизацию и поднять
`proxy-read-timeout` — это аннотации ingress-nginx. `OPENCRM_TRUSTED_PROXY_HOPS`
должен равняться числу прокси перед приложением, иначе ограничители по IP
считают весь трафик одним адресом ([07](07-bezopasnost.md)); нужен
`externalTrafficPolicy: Local` или proxy protocol.

### Пробы

`/healthz` проверяет базу, Redis, схему и режим техработ — годится для
readiness. Для liveness он опасен: при лежащей базе кластер начнёт
перезапускать здоровые поды по кругу. Нужна крошечная ручка вроде `/livez`,
отвечающая «процесс жив», — правка на десять строк.

### Бюджет соединений

Пул 5+5 на каждый рабочий процесс, `BYUDZHET_SOEDINENIY = 100`
(`database/session.py`). С N подами по два процесса нужно пересчитать
`max_connections` у MySQL и, возможно, поставить прокси (ProxySQL или Router из
InnoDB Cluster).

### Наблюдение

Стек Prometheus, Grafana, Loki из compose заменяется кластерным; `/metrics`
приложения остаётся. Метка старта процесса станет прыгать между подами — ей
нужна метка пода (это отмечено в [08](08-razvyortyvanie.md) для многопроцессного
режима).

## 3. Что даёт «без отказа», а что нет

Два и больше подов приложения дают переживание падения одного пода и обновление
без простоя. Без HA у MySQL и распределённого тома отказоустойчивости не будет:
упадёт узел с базой или томом — ляжет всё, только теперь в кластере.

Если переезд случится, порядок такой: сначала база и том, потом манифесты
приложения, sidecar nginx, CronJob, Ingress, `/livez`, Secret вместо
`config/.env`. Правки кода нужны маленькие: `/livez`, раздача медиа за флагом,
документация про режим без обновлятора. Всё остальное — манифесты или
Helm-чарт. Большая правка только одна, и она необязательная: S3 вместо диска.
