# 30 — Токены сотрудников: всё API для программ и агентов

Задание владельца от 28.09.2026: «чтобы модули, которые сейчас не поддерживают
API, могли работать через него, а в будущем через MCP — Claude агентом
управляет всей системой». Выбран вариант «токены к внутреннему API»:
сотрудник или отдельный «агент» получает токен и работает его ролью и
правами; все блоки доступны сразу, плюс машинное описание (OpenAPI) для MCP;
срок, отзыв, журнал, потолок запросов.

Это **не** API сайта ([16](../ustroystvo/16-api-sayta.md)). Тот — узкая дверь
наружу для чужой программы без сотрудника: шесть областей, свой склад, свой
заголовок. Токен — это сотрудник без браузера: тот же `/api/v1`, что зовут
экраны, те же права, те же отказы.

## 1. Как пользоваться

1. Настройки → API → «Токены сотрудников и агентов» → «Выпустить токен».
   Нужно право `settings.manage`.
2. Выбрать, **от чьего имени** действует токен. За коллегу выпускает только тот, у кого
   есть все его права, за root — только root: токен — это вход под человеком
   ([07](../ekspluatatsiya/07-bezopasnost.md), «Действовать за коллегу»). Агенту лучше завести
   отдельного сотрудника («Claude») с узкой ролью: токен умеет ровно то, что
   умеет роль, и ни строкой больше.
3. Срок — 30, 90, 180 дней, год или бессрочный (в списке красным).
   «Только чтение» — всё, кроме `GET`/`HEAD`, отвечает `403 token_read_only`.
4. Строку `ocrm_…` показывают **один раз** — в базе только отпечаток
   (sha256), как у сессий и ключей сайта.
5. Запросы — с заголовком:

```bash
curl -H "Authorization: Bearer ocrm_…" https://crm.example.com/api/v1/auth/me
```

Описание для MCP и генераторов клиентов — `GET /api/v1/system/openapi.json`
тем же заголовком (или сессией): OpenAPI 3.1 только тех маршрутов, куда токен
пустят, со схемой `bearer` и адресом сервера. Адрес берётся из `OPENCRM_BASE_URL`, а не
из запроса: uvicorn работает с `--no-proxy-headers`, и за nginx схема запроса всегда
`http` — MCP-клиент послал бы токен открытым текстом (разбор 28.09.2026).

## 2. Устройство

| Где | Что |
|---|---|
| `database/models/user_token.py` | `user_tokens`: сотрудник (CASCADE), имя, `prefix`, `token_hash` (unique), `tolko_chtenie`, кто выдал, срок, последнее обращение, отзыв |
| `core/services/token_service.py` | выдача, отзыв, вход (`voyti`), запреты (`ZAKRYTO`), потолок |
| `web/api/deps.py:get_current_user` | `Authorization: Bearer` → вход по токену; иначе cookie, как было |
| `web/api/opisanie.py` | сборка OpenAPI по маршрутам под входом минус запреты |
| `web/api/routes/tokens.py` | `GET/POST /tokens`, `POST /tokens/{id}/revoke` |
| `screens/SettingsTokens.tsx` | раздел на экране «API» |

Порядок проверок при входе: строка похожа на токен (приставка, ASCII, длина)
→ отпечаток найден → не отозван → не истёк → сотрудник активен → маршрут не
запрещён → не «только чтение» при записи → потолок. Дальше всё как у сессии:
`require_perm` проверяет блок и право.

**CSRF токену не нужен.** Двойная cookie защищает от чужой страницы, которая
шлёт запрос с cookie жертвы. Заголовок `Authorization` чужая страница прислать
не может без разрешения CORS, а его нет. Middleware проверяет CSRF только там,
где пришла cookie сессии, — это правило не менялось.

**Когда токены гаснут сами.** Сотрудник сменил свой пароль — все его токены
отозваны: свой пароль меняют и после угона, а токен, выпущенный угонщиком, иначе
пережил бы смену. Смена *временного* пароля (первый вход) токенов не трогает.
Отключение сотрудника отзывает токены насовсем — включение их не оживляет,
вернувшемуся выпускают новые (разбор 28.09.2026). Сброс пароля администратором
токены не трогает: так заводят сотрудника-агента, см. ниже.

**Временный пароль токену не мешает** (`require_staff`). Сотрудника-агента
заводят с временным паролем и не входят им никогда; пароль токен не
показывает, а «смените пароль» — защита именно пароля.

## 3. Куда токену нельзя — даже с правами root

Список `ZAKRYTO` в `token_service`, по шаблону пути внутри роутера:

| Что | Почему |
|---|---|
| `/tokens*` | токен не выпускает токенов: иначе отзыв одного ничего не отзывает |
| `/keys*` (сейф паролей) | пароль, попавший агенту, уже ушёл из системы — в его память и к его поставщику |
| `/system/backups*` | копия — это вся база одним файлом |
| `/settings/api-keys*` | выдача доступов — рукой человека |
| запись в `/roles*`, `/staff/{user_id}/role`, `/staff/{user_id}/approve` | раздача прав и допуск людей — рукой человека; иначе токен root'а делал root кого угодно |
| `/system/storage/purge`, `DELETE /system/files/{work_id}`, `DELETE /staff/{user_id}` | удаление насовсем: отменить нечем |
| `/staff/{user_id}/reset-password` | чужой пароль — это чужой вход |
| запись в `/auth*` | свой пароль, профиль, выход — дела человека; `GET /auth/me` открыт: агенту надо знать, кто он |
| `/live` | поток перепроверяет cookie на каждой доставке и закрылся бы молча |

Отказ — `403 token_not_allowed`. Сторож `tests/test_tokeny.py` требует, чтобы
каждая строка списка закрывала хотя бы один живой маршрут: переименованный
маршрут иначе открылся бы токену молча.

## 4. Журнал и потолок

Выдача и отзыв — записи `token.created` / `token.revoked` (источник «рука»).
Каждое изменение, сделанное токеном, пишется с источником **`token`** и
`source_ref` вида `#7 Claude`: службы пишут «рука», а `audit_service.record`
подменяет источник, если запрос пришёл по токену (`db.info[PO_TOKENU]`). Без
этого правка агента в журнале была бы неотличима от правки человека.

Само обращение в журнал не пишется — тысячи записей в сутки утопили бы
действия людей (так же решено у ключей сайта). Отметка «последнее обращение»
ставится не чаще раза в минуту и **вплотную к фиксации**, мимо ORM — ровно как
присутствие сотрудника: иначе строка токена была бы заперта весь запрос, и
параллельные запросы агента ждали бы друг друга (беда `1205` от 21.09.2026).

Потолок — **300 запросов в минуту на токен** (`V_MINUTU`), сверх — `429
token_rate_limited`. Угадывать токен бессмысленно (256 бит случайности), поэтому
промахи отдельно не считаются; настоящая беда — агент в цикле: команда,
безобидная в руках человека, из цикла уже валила боевое обновление.

## 5. MCP

Своего MCP-сервера в системе пока нет: он живёт у клиента (Claude Desktop,
Claude Code) и переводит OpenAPI в инструменты. Всё, что нужно ему от нас, —
токен и `/api/v1/system/openapi.json`. Описание собирается из тех же маршрутов,
что обслуживают экраны, поэтому новый маршрут появляется в нём сам, а
запрещённый токену — не появляется.

## 6. От чего отказались

- **Своих областей у токена нет** — только роль сотрудника. Две матрицы прав
  (роль и области токена) расходились бы, и «почему агенту нельзя» пришлось бы
  искать в двух местах.
- **Счётчика обращений в строке токена нет.** Запись на каждом запросе — это
  замок на строке и лишняя запись на самом частом пути; сколько ходил агент,
  видно по журналу изменений и по «последнему обращению».
- **Выпускать токен самому себе без `settings.manage` нельзя.** Токен живёт
  дольше сессии и уезжает в чужие конфиги; решает тот, кто решает про доступы.
