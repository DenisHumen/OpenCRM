# 04 — API

## Общее

- Базовый префикс внутреннего API: `/api/v1`. Публичные страницы витрины — вне API (см. раздел «Публичные маршруты»).
- Формат — JSON; загрузка файлов — `multipart/form-data`.
- Аутентификация — сессионная cookie (`HttpOnly`, `Secure`, `SameSite=Lax`). SPA и API живут на одном домене, поэтому cookie проще и безопаснее JWT в localStorage.
- Ошибки — единый формат:

```json
{ "error": { "code": "board_not_found", "message": "Board not found" } }
```

- Пагинация списков: `?page=1&per_page=50`, ответ содержит `items`, `total`, `page`, `per_page`.
- Все mutation-запросы защищены CSRF-токеном (double-submit cookie).

## Права

| Обозначение | Кто |
|---|---|
| 🔓 | без аутентификации |
| 👤 | любой активный сотрудник |
| 🔑 | нужно право «раздел.действие» из матрицы доступов |
| 👑 | только root (владелец системы; у него все права всегда) |

Права раздаются ролями, роли создаёт пользователь — разбор в
[07-security.md](07-security.md), реестр в `core/permissions.py`. Отказ —
`403 permission_denied` с именем недостающего права в сообщении. Порядок
проверок: **блок включён → есть право**, поэтому у выключенного блока ответ
`403 module_disabled`, даже если права нет тоже.

## Журнал действий (root)

Только чтение. Ручек записи и удаления **нет и не будет**: журнал дописывается
сервисами в той же транзакции, что и само изменение, а ручка «добавить запись»
позволила бы дописать в него что угодно и когда угодно — то есть отменила бы
весь смысл затеи не хуже, чем ручка «удалить» (см. [07-security.md](07-security.md)).

| Метод | Путь | Права | Описание |
|---|---|---|---|
| GET | `/audit` | 👑 | Журнал. Фильтры: `actor_id`, `entity_type`, `entity_id`, `source`, `action`, `search` (по имени человека и названию объекта), `since`, `until`; `page`/`per_page` (до 100) |

Запись ответа: `action`, `actor_id`, `actor_name` (снимок), `source`,

не было», пустая строка — «величина была пустой».

## Почта (блок `mail`)

Весь роутер закрыт `require_module("mail")`: при выключенном блоке любой маршрут отвечает **403 `module_disabled`** — не 404, потому что маршрут существует, его выключили. Ящик — настройка уровня фирмы, поэтому его CRUD и проверка соединения под 👑; читать почту и отправлять письма может любой сотрудник.

|---|---|---|---|
| GET | `/mail/accounts` | 👑 | Ящики фирмы. **Пароля в ответе нет никогда** — только `has_password` |
| POST | `/mail/accounts` | 👑 | Завести ящик: адрес, IMAP/SMTP, логин, `password` (уходит только внутрь) |
| PATCH | `/mail/accounts/{id}` | 👑 | Изменить. Пустой `password` = «не менять», а не «стереть» |
| DELETE | `/mail/accounts/{id}` | 👑 | Удалить ящик вместе с зеркалом его писем. Лента клиента остаётся |
| POST | `/mail/accounts/{id}/check` | 👑 | Проверка входа по IMAP и SMTP. Ответ `{ok, error}` — ошибка текстом, без пароля |
| POST | `/mail/accounts/{id}/sync` | 👤 | Ручная синхронизация. Доступна менеджеру: это чтение почты фирмы, а не правка настроек |
| GET | `/mail/messages` | 👤 | Список: `account_id`, `client_id`, `deal_id`, `direction=in\|out`, `unread`, `search`. Тела писем в списке не отдаются |

Письмо не заводит собственной истории: при появлении оно порождает запись общей ленты (`client_notes`, `kind='email'`, `direction`, `happened_at` = момент отправки письма). Входящее ищет клиента по адресу отправителя; нашли — привязали, не нашли — письмо остаётся непривязанным и **клиента не создаёт**: в ящик фирмы валятся рассылки, спам и ответы роботов, а «клиент» — решение человека.

## Шаблоны сообщений (блок `templates`)

Заготовка на то, что пишут снова и снова: первый ответ на заявку, ссылка на доску, напоминание об оплате. Шаблон — это `name` (уникальное), `body` с подстановками и `channel` (`any` / `email` / `note`) — где он применим. Универсальный шаблон попадает в выдачу по любому каналу: он для того и есть, чтобы один и тот же текст не держать в двух экземплярах.

Весь роутер закрыт `require_module("templates")`. Читать шаблоны может всякий, кто пишет клиентам (`templates.view`), править — тот, кому дано право.

| Метод | Путь | Права | Описание |
|---|---|---|---|
| GET | `/templates/fields` | 🔑 `templates.view` | **Закрытый набор полей**: `{key, needs}`, где `needs` — `""` / `client` / `deal`. Отдаётся с сервера, чтобы список не существовал во втором экземпляре во фронтенде |
| GET | `/templates` | 🔑 `templates.view` | Список по алфавиту. `?channel=email` — годные для письма (включая `any`); незнакомый канал — `422 unknown_channel`, а не пустая выдача, неотличимая от «шаблонов нет» |
| GET | `/templates/{id}` | 🔑 `templates.view` | Один шаблон |
| GET | `/templates/{id}/render` | 🔑 `templates.view` | Готовый текст: `?client_id=`, `?deal_id=` (оба необязательны). Ответ — `{template_id, name, channel, text, missing[], unknown[]}` |
| POST | `/templates` | 🔑 `templates.create` | Завести: `{name, body, channel?}`. Занятое название — `409 template_name_taken` |
| PATCH | `/templates/{id}` | 🔑 `templates.edit` | Изменить любое из трёх полей |
| DELETE | `/templates/{id}` | 🔑 `templates.delete` | Удалить. Уже отправленные сообщения не меняются: применённый шаблон давно стал самостоятельным письмом или записью ленты и связи с шаблоном не хранит |

`render` сделан `GET`'ом намеренно: подстановка ничего не создаёт и не меняет. POST пришлось бы закрывать правом на правку — и смотреть готовый текст смог бы только тот, кому разрешено править сами шаблоны, то есть ровно наоборот тому, ради чего блок заводился.

### Подстановки

Пишутся как `{client_name}`. Всё остальное в фигурных скобках (`{ }`, кусок JSON) — обычный текст: подстановка — это скобки с именем внутри, и отвергать всё подряд значило бы запретить написать скобку, которую имели в виду буквально.

**Набор закрыт и объявлен в коде** (`core/services/template_service.py`). Сейчас в нём шесть полей: `client_name`, `client_company`, `deal_title`, `deal_number`, `board_url`, `company_name`. Открытый набор («любое поле модели») означал бы письмо клиенту с себестоимостью его же заказа, поэтому значения считает поимённый список, а не `getattr` по присланному имени.

Четыре правила, которые важнее самих полей:

- **Неизвестная подстановка не проходит молча.** При сохранении — `422 unknown_placeholder` с перечислением **всех** виноватых (`{clietn_name}`, `{deal_amount}`). Тихая пустота означала бы «Здравствуйте, !» в письме клиенту, и это увидели бы все, кроме автора шаблона.
- **Поле, убранное из набора после того, как шаблон написали**, подставляется видимой пометкой `[?имя]` и попадает в `unknown`. Пустотой оно не становится никогда.
- **Законно пустого значения не бывает «просто пусто».** У клиента может не быть фирмы, у заявки — доски; такое поле подставляется тире (`—`) и называется в `missing`. Прочерк без списка приняли бы за опечатку в шаблоне, список без прочерка не спас бы от «Фирма: » посреди предложения. Слово вместо тире не подставляется намеренно: тело пишут на своём языке, и английская заплатка посреди русского письма хуже честного прочерка.
- **Подставленное не управляет подстановкой.** Значение вставляется буквально (`\1` и `<b>` в имени клиента остаются собой), один проход (клиент по имени «ООО {board_url}» не вытащит чужую ссылку) и в одну строку (имя с переводами строк не дописывает в письмо абзац «P.S. переведите деньги на другой счёт»).

`missing` и `unknown` приходят **всегда**, пустыми списками в том числе: форма ответа не зависит от того, повезло ли с данными, — то же правило, что у выключенных блоков в сводке.

Откуда берутся значения: `deal_number` — это `#{id}` заявки (своего ряда номеров у заявок нет: номер печатают на бланке, а заявку называют словами). `board_url` — **живая** ссылка доски заявки (отозванная и просроченная не годятся: они ведут на страницу с отказом); из нескольких берётся самая ранняя, чтобы ответ не плавал между вызовами. `company_name` — фирма заявки → основная фирма → название бизнеса из настроек. Выключенные блоки `boards` и `companies` в шаблон **не подтекают**: поле становится прочерком, иначе «выключено» означало бы лишь «не видно в меню».

Клиент и заявка обязаны сходиться: заявка чужого клиента — `422 deal_other_client`, тот же код, что у письма и у звонка. Заявка указана, клиент нет — клиент берётся у заявки. Без обоих `render` тоже отвечает: это предпросмотр, где поля про них прочерки.

## Склад (блок `warehouse`, по умолчанию выключен)

Раздел закрыт `require_module("warehouse")`: при выключенном блоке любой из этих
адресов отвечает `403 module_disabled`.

**Остаток не хранится.** Он равен сумме движений и считается запросом, поэтому
колонки «остаток» у товара нет, а `stock_milli` в ответах — всегда результат
агрегата. Количество — целое в тысячных долях единицы (1.25 кг → `1250`), деньги —
целые в минимальных единицах, как везде. У услуги `stock_milli` равен `null`, а
не `0`.

| Метод | Путь | Права | Описание |
|---|---|---|---|
| GET | `/warehouse/products` | 👤 | Список с остатками. `search`, `low_only`, `include_services`, пагинация |
| POST | `/warehouse/products` | 👤 | Создать позицию. `sku` уникален, но необязателен (пусто → `NULL`); `409 sku_taken` |
| GET | `/warehouse/products/{id}` | 👤 | Карточка с остатком |
| PATCH | `/warehouse/products/{id}` | 👤 | Изменить. Товар с остатком нельзя сделать услугой (`422 product_has_stock`) |
| DELETE | `/warehouse/products/{id}` | 👤 | Мягкое удаление. Движения остаются |
| POST | `/warehouse/products/{id}/restore` | 👤 | Вернуть из корзины |
| GET | `/warehouse/products/{id}/moves` | 👤 | История по товару + `stock_milli` (агрегат, а не сумма страницы) |
| GET | `/warehouse/moves` | 👤 | Движения. Фильтры `product_id`, `deal_id`; при `deal_id` в ответе `cost` — себестоимость списанного под заявку |
| POST | `/warehouse/moves` | 👤 | Записать движение. Виды: `in`, `out`, `writeoff`, `adjust`, `return` |

Про `POST /warehouse/moves`:

- Расход и списание всегда уменьшают остаток, какой бы знак ни прислали.
- **Уход в минус разрешён** и помечается флагом `went_negative` в ответе: товар
  часто отдают раньше, чем заносят приход, и запрет заставил бы либо не
  записывать расход, либо выдумывать приход. Обе лжи хуже честного минуса.
- `quantity` принимается строкой и разбирается на сервере через `Decimal`.
  Лишние знаки после запятой отвергаются (`422 quantity_too_precise`), а не
  округляются: молчаливое округление и есть причина, по которой одно и то же
  списывают дважды.
- Нулевое количество — `422 zero_quantity`; движение по услуге — `422
  service_has_no_stock`; несуществующая заявка — `404 deal_not_found`.
- Движение не редактируется и не удаляется: ошибку исправляют обратным движением.
## Телефония (блок `telephony`)

| Метод | Путь | Права | Описание |
|---|---|---|---|
| GET | `/telephony/calls` | 👤 | Журнал: `?direction=in\|out`, `?outcome=`, `?client_id=`, `?deal_id=`, `?user_id=`, `?number=` (приводится к нормализованному виду), `?since=`, `?until=`, пагинация. Незнакомое значение `direction`/`outcome` — `422`, а не пустая выдача, неотличимая от «звонков нет» |
| GET | `/telephony/calls/{id}` | 👤 | Карточка звонка |
| PATCH | `/telephony/calls/{id}` | 👤 | Привязать разговор к заявке или отвязать: `{"deal_id": 7 \| null}`. `422 deal_other_client` — заявка чужого клиента |
| POST | `/telephony/calls/{id}/callback-task` | 👤 | Напоминание перезвонить по пропущенному. `422 call_not_missed`, `409 module_disabled` — блок напоминаний выключен |
| POST | `/telephony/click-to-call` | 👤 | Просит АТС набрать: `{"number": "…", "from_ext": "…", "deal_id": 7}`. `422 telephony_not_configured`, `400 pbx_unavailable`, `409 pbx_call_id_taken` — станция выдала ключ, который уже занят прошлым разговором |
| GET | `/telephony/settings` | 👑 | Настройки подключения. Секреты не отдаются — только `has_api_token` / `has_webhook_secret` |
| PATCH | `/telephony/settings` | 👑 | Провайдер, адрес команды набора, токен, внутренний номер, смещение зоны АТС, код страны. `422 bad_telephony_url` — адрес станции не http(s) или слишком длинный |
| POST | `/telephony/settings/secret` | 👑 | Новый секрет подписи вебхука; возвращается **один раз** |
| POST | `/telephony/webhook` | 🔓 | События звонка от АТС. Подпись обязательна (см. [07-security.md](07-security.md)) |

Поля звонка: `duration_sec = null` — длительность неизвестна (не то же, что `0`),
`outcome = null` — звонок ещё идёт. `counterparty` — номер собеседника: у входящего это
звонивший, у исходящего — вызываемый.

Формат события вебхука: `call_id` (обязателен), `direction`, `from`, `to`, `started_at`
(ISO 8601, лучше со смещением), `duration`, `outcome`, `recording`, `operator_email`.
Клиента в теле не спрашиваем и не принимаем — он определяется по номеру.

Вебхук **не закрыт блоком**: у АТС нет способа узнать, что владелец выключил телефонию,
и на ошибку она уходит в ретраи. При выключенном блоке запрос принимается (`200`) с телом
`{"status": "ignored", "reason": "module_disabled"}` и ничего не пишет; подпись
проверяется в любом случае.

## Телеграм: переписка с клиентами (блок `telegram`)

Один бот фирмы, общение только один на один. **Клиент обязан начать разговор
сам** — телеграм не позволяет боту написать первым тому, кто его не запускал;
отсюда ручка приглашения со ссылкой и QR-кодом.

| Метод | Путь | Права | Описание |
|---|---|---|---|
| GET | `/telegram/settings` | 👑 | Состояние подключения. Токен НЕ отдаётся — только `token_tail` из четырёх знаков и признаки `configured` / `webhook_secret_set` |
| PUT | `/telegram/settings` | 👑 | Токен, имя бота, чат утренней сводки. Пустой токен означает «не меняй»: экран настоящего не знает и вернуть не может. `422 bad_bot_token`, `422 bad_chat_id` |
| DELETE | `/telegram/settings` | 👑 | Отключить бота: снимает вебхук у телеграма и стирает токен с секретом. **Переписка остаётся** — отключение про связь, а не про данные |
| POST | `/telegram/connect` | 👑 | Сказать телеграму, куда доставлять (`setWebhook`). Отдельно от сохранения токена: адрес зависит от того, как сайт виден снаружи, и меняется при переезде. `422 telegram_needs_https` — телеграм принимает вебхук только по HTTPS |
| GET | `/telegram/invite` | 👤 | Ссылка `t.me/имя?start=метка` и QR-код к ней. `?label=` — только буквы, цифры, дефис и подчёркивание (требование телеграма). `422 telegram_username_missing` |
| GET | `/telegram/chats` | 👤 | Диалоги, свежие сверху: `?q=`, `?source=` (метка из ссылки, точным совпадением, а не подстрокой), пагинация. У каждого `unread` — **личный** счётчик непрочитанного, `has_avatar` (стоит ли просить картинку) и `is_premium` |
| PATCH | `/telegram/chats/{id}` | 👤 | Привязать диалог к карточке клиента или отвязать: `{"client_id": 7 \| null}`. Только руками: автоматически связывается лишь точное совпадение номера |
| POST | `/telegram/chats/{id}/deal` | 🔑 `deals.create` | Завести заявку по переписке. Право спрашивается на ЗАЯВКИ, а не на телеграм: заводится заявка, и решать, кому это можно, должен её раздел. Диалог обязан быть привязан к карточке — `422 telegram_chat_not_linked`, заявка без клиента бессмысленна. Пустое название берётся из последнего входящего |
| POST | `/telegram/chats/{id}/task` | 🔑 `tasks.create` | Завести напоминание по переписке. Привязки к карточке НЕ требует: «перезвонить этому человеку» осмысленно и до того, как выяснили, кто он. Привязан диалог — клиент подставится |
| GET | `/telegram/chats/{id}/messages` | 👤 | Лента. `?before=` — листание вглубь по идентификатору (не по смещению: на живой переписке оно врёт), `?after=` — дочитать пропущенное после обрыва. Показ ленты сдвигает границу «прочитано» |
| POST | `/telegram/chats/{id}/messages` | 👤 | Ответить текстом. Строка заводится ДО обращения к телеграму, поэтому двойное нажатие не отправляет дважды. Отказ телеграма не откатывает запись: `send_state=failed` и причина в `send_error` |
| POST | `/telegram/chats/{id}/files` | 👤 | Ответить файлом: картинка, видео или документ |
| GET | `/telegram/chats/{id}/messages/{msg}/file` | 👤 | Отдать вложение. Через приложение, а не статикой: переписка с клиентом не публичная картинка, и ссылка не должна работать у всякого, кто её узнал |
| POST | `/telegram/chats/{id}/messages/{msg}/fetch` | 👤 | Забрать видео, которое сразу не тянули. Идемпотентно |
| POST | `/telegram/chats/{id}/read` | 👤 | «Я это увидел»: сдвигает личную границу прочитанного. Нужна потому, что дочитывание (`?after=`) границу НЕ двигает — оно приносит сообщения и в свёрнутую вкладку. Различает эти два случая только браузер |
| GET | `/telegram/chats/{id}/avatar` | 👤 | Фотография профиля собеседника. Освежается по требованию, но не чаще раза в сутки: аватар не приходит с сообщением, за ним надо ходить отдельно. `404 telegram_no_avatar` — обычное дело, а не отказ: экран рисует инициалы |
| GET | `/telegram/chats/{id}/emoji` | 👤 | Именной эмодзи собеседника — статичной картинкой: сам эмодзи Lottie, и браузер его не рисует. Забирается при приёме сообщения, не чаще раза в сутки и только у премиума. `404 telegram_no_emoji` — как и у аватара, обычное дело, а не отказ |
| POST | `/telegram/chats/{id}/presence` | 👤 | «Я в этом чате» / «ушёл». Отвечает списком смотрящих. Ключ со сроком годности в Redis — уборки не требует |
| GET | `/telegram/stream` | 👤 | Поток событий (SSE): новые сообщения и смена присутствия. Соединение живёт пять минут, дальше браузер переподключается сам |
| POST | `/telegram/digest/send` | 👑 | Отправить утреннюю сводку прямо сейчас — посмотреть оформление, не дожидаясь утра |
| POST | `/telegram/webhook` | 🔓 | Обновление от телеграма. Секрет заголовком `X-Telegram-Bot-Api-Secret-Token`; сверка постоянным временем, ограничитель ДО сверки |

Приём отвечает **200 почти всегда**: любой иной ответ телеграм считает
недоставкой и повторяет часами. Отказом отвечаем ровно на неверный секрет.

## Заявки с сайта

| Метод | Путь | Права | Описание |
|---|---|---|---|
| POST | `/public/leads` | 🔓 | Заявка с формы на сайте. Ключ приёма — в заголовке `X-OpenCRM-Intake-Key`. Ответ всегда `202 {"status": "accepted"}` |

Тело: `name`, `email`, `phone`, `message`, `website`. Обязательного поля как такового
нет, но **почта или телефон нужны хотя бы одно** — иначе `422 contact_required`:
заявка, по которой не с кем связаться, даёт пустую строку в справочнике.

`website` — **ловушка**. В форме поле скрывается стилями: человек его не видит и не
заполняет, бот заполняет всё подряд. Заполненное поле означает, что заявка не
записывается вовсе, а ответ при этом выглядит как успех — скажи мы «отказано»,
подбирающий за десяток попыток вычислил бы лишнее поле и перестал его трогать.

Что происходит с принятой заявкой:

- клиент ищется по присланному адресу (сравнение через `lower()`, целиком — `_` и `%`
  в адресе это знаки, а не шаблон) и по нормализованному номеру (`phone_norm`, то есть
  `067…` находит карточку с `+380 67…`). Нашёлся — заявка цепляется к нему, **второй
  карточки не будет**; известную карточку форма при этом не правит: знание чужого
  номера не должно давать права переписать в ней почту;
- не нашёлся — заводится карточка с меткой `lead` и источником `site` (отдельной
  колонки «статус» в системе нет; метка фильтруется списком клиентов, источник
  считается отчётом по источникам);
- заводится заявка на **первом открытом этапе воронки** — на том, что настроен у
  бизнеса, а не на зашитом;
- ответственный получает напоминание (блок `tasks`; выключен — заявка принимается
  без напоминания). Кто ответственный — настройка `leads_manager_id`; не задана или
  сотрудник отключён — заявки достаются владельцу системы.

Ответ **одинаковый всегда**: ни идентификатора клиента, ни номера заявки, ни слова о
том, завели карточку или узнали своего. Иначе по разнице ответов кто угодно проверял
бы, есть ли такой человек в базе.

Отказы: `401 intake_not_configured` — ключ приёма не задан, приёма нет вовсе (так
выглядит свежая установка); `401 bad_intake_key`; `413 body_too_large` — тело больше
мегабайта, отсекается по `Content-Length` **до чтения**; `422 bad_email`,
`422 email_too_long`, `422 phone_too_long` — адрес и номер не обрезаются, обрезанный
адрес это другой адрес; `429 lead_rate_limited` — слишком часто с одного адреса
(30 за 10 минут, считаются все обращения, а не одни отказы);
`429 lead_intake_flooded` — форма завела больше 60 новых карточек за час.

Повтор той же заявки в течение 5 минут (двойное нажатие, повторная доставка с сайта)
цепляется к уже заведённой работе: ни второй карточки на доске, ни второго напоминания.

**Заявку шлёт сервер сайта, а не страница в браузере.** Ключ, вставленный в HTML,
знает каждый посетитель; и принимается только JSON — тело другого типа проходит мимо
потолка размера. Ключ здесь не подпись: он закрывает ручку от сканеров и даёт способ
отозвать доступ, но не доказывает, что тело не подменили (у формы нет места, где
хранить секрет, — в отличие от АТС). От потока защищают ограничитель и потолки.

Настройки блока (`site_settings`, в общий `GET /settings` не входят): `leads_intake_key`
— сам ключ, `leads_manager_id` — ответственный.
