# 04 — API

## Общее

- Базовый префикс внутреннего API: `/api/v1`. Публичные страницы витрины — вне API (см. раздел «Публичные маршруты»).
- Формат — JSON; загрузка файлов — `multipart/form-data`.
- Аутентификация — сессионная cookie (`HttpOnly`, `Secure`, `SameSite=Lax`). SPA и API живут на одном домене, поэтому cookie проще и безопаснее JWT в localStorage.
- Ошибки — единый формат:

```json
{ "error": { "code": "board_not_found", "message": "Board not found" } }
```

- Пагинация — у длинных списков: `?page=1&per_page=50`, ответ содержит `items`, `total`,
  `page`, `per_page` (`schemas.paginated`). Справочники и короткие наборы страниц не имеют
  вовсе и отвечают одним `items`: сотрудники, роли, коллеги, шаблоны, напоминания, фирмы,
  этапы воронки, блоки, склады, файлы клиента, лента переписки. Страница у списка из шести
  строк обязывает клиента её листать и ничего взамен не даёт.
- Все mutation-запросы защищены CSRF-токеном (double-submit cookie).

## Права

| Обозначение | Кто |
|---|---|
| 🔓 | без аутентификации |
| 👤 | любой активный сотрудник |
| 🔑 | нужно право «раздел.действие» из матрицы доступов |

Права раздаются ролями, роли создаёт пользователь — разбор в
[07-security.md](07-security.md), реестр в `core/permissions.py`. Отказ —
`403 permission_denied` с именем недостающего права в сообщении. Порядок
проверок: **блок включён → есть право**, поэтому у выключенного блока ответ
`403 module_disabled`, даже если права нет тоже.

**Значка «только root» в таблицах нет ни у одного маршрута.** Зависимости
`require_root` в `web/api/deps.py` больше не существует: «нужен root» перестало
быть ответом на вопрос «кому можно» — должность «гендиректор» заводит ящики и
переключает блоки, не будучи владельцем системы. Останься эта зависимость, она
стала бы удобным способом закрыть очередной маршрут мимо матрицы, и матрица
начала бы врать о том, что настраивает. Сам root никуда не делся:
`permissions_service.has` отдаёт ему все права всегда, поэтому 🔑 он проходит
везде.

## Аутентификация и аккаунт

| Метод | Путь | Права | Описание |
|---|---|---|---|
| POST | `/auth/register` | 🔓 | Заявка на аккаунт менеджера: `name, email, password`. Ответ — «ожидайте одобрения» |
| POST | `/auth/login` | 🔓 | Вход. `403 account_pending` — не одобрен, `403 account_disabled` — деактивирован |
| POST | `/auth/logout` | 👤 | Выход |
| GET | `/auth/me` | 👤 | Текущий пользователь: имя, `role` (root или нет), `role_id`/`role_name` (должность), `permissions` — текущий набор прав, `locale`, `must_change_password`, `avatar_url`, `is_online`, `last_seen_at`. Права читаются на каждый запрос, а не запоминаются при входе |
| PATCH | `/auth/me` | 👤 | Смена имени, `locale` (en/ru — сохраняется в БД) |
| POST | `/auth/me/password` | 👤 | Смена пароля (старый + новый); сбрасывает `must_change_password` |
| GET | `/auth/heartbeat` | 👤 | Пинг присутствия: обновляет `last_seen` (фронт шлёт раз в ~45 c, пока вкладка активна) |
| POST | `/auth/me/avatar` | 👤 | Загрузить свой аватар (растр по сигнатуре, не SVG; обрезается в квадрат 256, webp) |
| DELETE | `/auth/me/avatar` | 👤 | Убрать аватар (файл стирается с диска) |

Присутствие: `last_seen_at` на пользователе обновляется на активность не чаще раза в минуту и
переживает logout (остаётся «последний раз в сети»); `is_online` = активность за последние 150 c.
Аватары отдаёт `GET /avatars/{uuid}.webp` (публичный путь, как `/branding`).

## Коллеги и рабочее пространство

Две ручки, открытые любому сотруднику. Обе существуют потому, что соседние
разделы закрыты правом, а нужное с них — нет.

| Метод | Путь | Права | Описание |
|---|---|---|---|
| GET | `/people` | 👤 | Коллеги для выпадающего списка «ответственный»: `id`, имя, аватар активных сотрудников. Отдельно от `/staff`: назначать заявку на коллегу должен всякий, а знать при этом чужие адреса, статусы и даты одобрения — незачем |
| GET | `/workspace` | 👤 | `brand_name`, `currency`, `deal_term`. Полные настройки читает не каждый, а валюта и слово для заявки нужны на каждом экране: без них суммы показываются без обозначения, а разделы называются чужими словами |

`/workspace` завёлся вместо копирования этих трёх полей в ответы заявок, досок и
клиентов: копий набралось три, и они начали расходиться.

## Блоки системы

Реестр блоков — `core/modules.py`, в базе только «включён/выключен». На эти
ручки опираются все упоминания `module_disabled` в остальном документе.

| Метод | Путь | Права | Описание |
|---|---|---|---|
| GET | `/modules` | 👤 | Что включено, кем и когда. Права нет намеренно: интерфейсу надо знать, что рисовать в меню, — а это ровно каждый сотрудник |
| GET | `/modules/presets` | 🔑 `settings.manage` | Наборы блоков под тип дела: состав, `will_enable` (чего ещё нет), воронка и слово для заявки. Состав считает сервер — список ключей во фронтенде разошёлся бы с реестром на первом же новом блоке |
| POST | `/modules/presets` | 🔑 `settings.manage` | Применить набор: `{key, apply_pipeline?, apply_deal_term?}`. Набор **только включает** — блоки вне него остаются как есть |
| POST | `/modules/{key}` | 🔑 `settings.manage` | Переключить один блок: `{"enabled": true\|false}` |

Забрать раздел с данными одним нажатием — самый быстрый способ потерять доверие,
поэтому пресет не выключает ничего. Воронка и слово для заявки ставятся вместе с
блоками: человек отвечал на вопрос «чем вы занимаетесь», а не «какие разделы
показать»; отменяется это двумя флагами — для того, кто вернулся к экрану уже с
настроенной воронкой.

## Поиск и дашборд

| Метод | Путь | Права | Описание |
|---|---|---|---|
| GET | `/search?q=` | 👤 | Общий поиск для командной палитры (Ctrl+K). Три группы в порядке левой колонки — `clients`, `deals`, `boards`, — по первой странице (6 записей) в каждой. Пустой `q` — недавние записи |
| GET | `/search/{area}?q=&page=` | 👤 | Продолжение ОДНОЙ группы — «показать ещё» в палитре. `area` — ключ группы из общего поиска, неизвестный даёт 404. Отвечает той же формой, что группа: `items`, `total`, `has_more` |
| GET | `/dashboard` | 👤 | Сводка: деньги с начала месяца, воронка со счётчиками, мои задачи на сегодня, просмотры за 7 дней, недавние доски и клиенты |

Группа поиска **пустеет, но не исчезает**: выключенный блок или отсутствие
`<область>.view` дают пустой список под тем же ключом. Форма ответа одна при
любом наборе блоков и прав, и клиенту не приходится знать, какие ключи сегодня
бывают. Обе проверки обязательны: без первой доски находились бы поиском и вели
в раздел, которого нет ни в меню, ни в маршрутах; без второй поиск стал бы
обходом доступов — через него видны имена и названия из закрытого раздела.
Заявки дополнительно сужает `deals.view_others`, суммы прячет `deals.view_amounts`.

**Выдача листается по группам, а не обрывается на первой странице.** Шестёрка —
размер страницы, а не потолок: одно время она была потолком, и на «be» палитра
показывала ровно шесть досок, а седьмую нельзя было достать ничем. Номер
страницы приходит только в `/search/{area}`: общий поиск отдаёт первые страницы
всех групп разом, а один `page` на три группы означал бы вторую страницу у
досок, у которых нашлось двадцать, и её же у клиентов, у которых нашлось два.
Группы кончаются порознь, потому и листаются порознь. Продолжение закрыто теми
же проверками, что и первая страница (сначала блок, потом право), — иначе оно и
было бы обходом: закрытый раздел не отдаёт первую страницу, но отдаёт вторую.

**Точного числа найденного в поиске нет и не будет.** `total` — это длина
показанного, а «есть ли ещё» отвечает `has_more`. Точный счёт означал второй
полный проход по таблице на каждую группу и стоил ровно столько же, сколько сама
выборка: на 400 000 заявок 3128 мс против 3165 мс — секунды на число, которое
клиент выбрасывал не глядя. Полноту выдачи это не ограничивает: листается она по
`has_more`, а не по остатку от `total`. Точный `total` живёт на экранах разделов,
где из него считается номер последней страницы.

Ключи ответа `/dashboard`: `currency`, `money_in_work`, `money_won_this_month`,
`money_received_this_month`, `money_basis`, `avg_check`, `won_count_this_month`,
`deals_by_stage`, `my_tasks`,
`clients_total`, `clients_this_month`, `boards_total`, `boards_published`,
`views_7d`, `views_prev_7d`, `unique_viewers_7d`, `views_by_day`, `last_view_at`,
`recent_boards`, `recent_clients`. **При выключенном блоке ключи остаются, а
значения пустеют** — то же правило, что у поиска. Деньги считаются с начала
календарного месяца, а не за последние 30 дней: владелец сверяет их с месячной
отчётностью, и скользящее окно давало бы число, которое ни с чем не сходится.
`deals.view_others` сужает и числа тоже — спрятать чужие карточки и оставить их
сумму значит не запретить ничего, узнать оборот фирмы и было целью. Без
`deals.view_amounts` денежные плитки приходят пустыми, кроме `won_count`:
«сколько сделок я выиграл» — не сумма, и прятать его вместе с суммами значило бы
отнимать число, которое человек и так видит в своём списке.

`money_received_this_month` — сколько **пришло в кассу** с первого числа; по
решению «банк один» это и есть выручка, и именно здесь владелец видел пустой
месяц при полной кассе. Плитка стоит рядом с `money_won_this_month`, а не вместо
неё: это два разных вопроса («получили» и «продали на»), и расхождение между ними
— полезное число. Пусто и `money_basis == "deals"` — блок «Финансы» выключен,
полученных денег система не ведёт, и экран говорит это подписью.

## Хранилище и состояние системы

| Метод | Путь | Права | Описание |
|---|---|---|---|
| GET | `/system/storage` | 👤 | Место на диске: занято/свободно, размер `storage/`, объём корзины, уровень тревоги, блокирована ли загрузка |
| POST | `/system/storage/purge` | 🔑 `settings.manage` | Окончательно удалить мягко удалённое: доски, работы, клиентов, заявки и файлы клиентов. Отвечает счётчиками по каждому виду и свежим состоянием хранилища |
| GET | `/system/files` | 🔑 `settings.manage` | Менеджер файлов: все работы досок — размер на диске, дата загрузки, дата последнего просмотра доски, превью |
| DELETE | `/system/files/{work_id}` | 🔑 `settings.manage` | Удалить одну работу вместе с файлами; отвечает свежим статусом хранилища |
| GET | `/system/schema` | 🔑 `settings.manage` | Сходится ли живая база с моделями — подробно, для разбора |
| GET | `/system/monitoring` | 🔑 `monitoring.view` | Состояние стека наблюдения и путь к панели |

`purge` — **единственное место в системе, где данные исчезают безвозвратно**,
поэтому вызов пишется в журнал действий (`ACTION_STORAGE_PURGED`) с перечнем
того, что ушло. Раньше не писался вовсе: человек освобождал диск, а что при этом
удалилось, выяснить потом было не по чему. Клиента с выигранной заявкой purge не
трогает — это полученные деньги.

`/system/schema` отвечает тем же отчётом, который снят на старте приложения
(`web/main.py`): схема не меняется, пока процесс живёт. Коротко о том же говорит
`/healthz`, но там деталей нет намеренно — он открыт наружу. Это и есть способ
посмотреть состояние на живой машине, на который ссылается `CLAUDE.md`; разбор
самой гарантии — в [08-deployment.md](08-deployment.md).

У мониторинга **своё право, а не `settings.manage`**: дежурного по серверу можно
пустить к панели, не отдавая ему логотип сайта и переключатели блоков. Заодно это
даёт правильный порядок «блок включён → есть право» даром — при выключенном
мониторинге сюда приходит `module_disabled`. Отдельная ручка, а не поле в
`/modules`: там отвечают на вопрос «нажат ли флажок в базе», и ответ обязан быть
мгновенным, его ждёт каждое меню, — а здесь ходят по сети к соседним контейнерам.

## Клиенты

Адрес для отправки: `country` (код ISO 3166-1 alpha-2), `city`, `zip_code`,
`address` — принимаются в `POST` и `PATCH`, отдаются в ответе. Не назвали
`country`, но назвали телефон — страна определяется по коду набора и
**едет за номером**, пока её не назвали руками. Общие коды (`+1`) страны не
дают: флаг наугад хуже отсутствующего. Отказы: `country_invalid` (не два
знака), `city_too_long`, `zip_too_long`, `address_too_long`.

| Метод | Путь | Права | Описание |
|---|---|---|---|
| GET | `/clients` | 🔑 `clients.view` | Список: `?search=`, `?tag=`, `?manager_id=`, пагинация, сортировка по обновлению |
| POST | `/clients` | 🔑 `clients.create` | Создать карточку |
| GET | `/clients/{id}` | 🔑 `clients.view` | Карточка целиком: контакты, последние заметки, файлы, связанные доски |
| PATCH | `/clients/{id}` | 🔑 `clients.edit` | Обновить поля |
| DELETE | `/clients/{id}` | 🔑 `clients.delete` | Мягкое удаление |
| POST | `/clients/{id}/restore` | 🔑 `clients.restore` | Вернуть из корзины |
| GET | `/clients/{id}/notes` | 🔑 `clients.view` | Лента истории (пагинация). Фильтры `kind` и `deal_id` |
| POST | `/clients/{id}/notes` | 🔑 `clients.edit` | Добавить запись: `kind` (note/call/meeting/email), `body`, `happened_at`, `direction`, `deal_id` |
| DELETE | `/clients/{id}/notes/{note_id}` | 🔑 `clients.edit` | Удалить запись |
| GET | `/clients/{id}/files` | 🔑 `clients.view` | Список файлов (одним `items`, без страниц) |
| POST | `/clients/{id}/files` | 🔑 `clients.edit` | Загрузить файл (multipart) |
| GET | `/clients/{id}/files/{file_id}/download` | 🔑 `clients.view` | Скачать (через приложение, с проверкой сессии) |
| DELETE | `/clients/{id}/files/{file_id}` | 🔑 `clients.edit` | Удалить файл |

`restore` — отдельное действие, а не оборотная сторона `delete`: удалять рутина,
поднимать удалённое — разбор происшествия, и это разные полномочия. Запись ленты
и файл ходят под `clients.edit`, а не под своими правами: они и есть правка
карточки, а дробить «изменить телефон» и «дописать заметку» не на что.

## Заявки (блок `deals`, несущий)

Запланировано: строки заявки (товары со склада и свои траты), бронь под заявку, списание при закрытии, заказ из заявки — [19](19-sborka-zakaza.md) §6.1, §6.3.

Заявка — стержень системы: на ней сходятся этапы, лента, бланки, склад и деньги.
Блок объявлен несущим в `core/modules.py` и выключить его нельзя — это рассыпало
бы систему на несвязанные списки, ради связывания которых всё и затевалось.

| Метод | Путь | Права | Описание |
|---|---|---|---|

| POST | `/deals/{id}/feed` | 🔑 `deals.edit` | Дописать в ленту (то же тело, что у заметки клиента) |

**Двигать заявку — отдельное право.** Вести заявку и решать, что она
«выполнена», — разные полномочия: на этапе `won` считается выручка.

**Один и тот же список у двух сотрудников разный, и это два сужения, а не
настройка интерфейса.**

- `deals.view_others` решает, ЧЬИ заявки видно. Без права человек видит только
  те, где он ответственный, — и это фильтр в запросах, а не признак на экране:
  спрятать чужие карточки в вёрстке значит оставить их доступными по адресу, в
  поиске, на сводке и в выгрузке отчёта. Прямой запрос чужой заявки отвечает
  `403 permission_denied` с именем недостающего права, а не «не найдено»: заявка
  существует, и сотрудник о ней обычно знает — коллега прислал ссылку. Молчаливое
  404 солгало бы дважды и не подсказало, что просить у того, кто раздаёт доступы.
- `deals.view_amounts` решает, видно ли деньги. Самая частая просьба и главная
  причина, по которой прав на раздел недостаточно: менеджер ведёт заявку, но не
  видит её маржу. Право закрывает суммы **и на запись тоже** — не видит сумм, не
  называет их ни при заведении, ни при правке. Иначе оно было бы наполовину
  декоративным: сумму не показали, но её можно перезаписать вслепую, а прежнее
  значение при этом теряется без следа. Итог над колонкой канбана прячется вместе
  с карточками — одно без другого это скрытая сумма, которую видно в шапке.

Ответ на `PATCH` и `POST /move` — **такая же карточка, как у `GET`**. Разная
форма уже ломала экран: фронт клал ответ `PATCH` в состояние, `stage_history`
оказывалась `undefined`, и после смены этапа карточка уходила в белое.

Отдельной ленты у заявки в базе нет — это записи ленты клиента с проставленным
`deal_id`. Отдельная точка, а не фильтр в ленте клиента, потому что спрашивать
события заявки через клиента значит каждый раз помнить, чей это клиент.

**Режим обслуживания — не мелочь среди логотипов.** Включённый, он отвечает
`503` и сотруднику, и посетителю витрины; владелец при этом проходит по
устройству режима. Лежит он в настройках, то есть в базе, и потому переживает
пересборку контейнера — а включает его не только человек: его ставит и снимает
переезд базы (`migrate_maintenance` в `opencrm.sh`). Убитый посреди переноса
переезд оставляет сайт закрытым навсегда, и проверено делом, что этого не видит
никто: `/healthz` отвечал «всё в порядке», докер, автообновление и мониторинг
молчали, а единственный, кто может починить, видел рабочий сайт. Поэтому режим
попал отдельной строкой в `/healthz` (`maintenance: on|off`) — но **кода ответа
не меняет**: на 200 завязаны проверка здоровья docker и откат обновления, а они
умеют одно — заменить контейнер приложения. Закрытый сайт этим не чинится, зато
цикл перезапусков поверх обслуживания превратил бы объявленную работу в
настоящую аварию. Разбор целиком — в `web/main.py:healthz` и
[08-deployment.md](08-deployment.md).

## Журнал действий

Только чтение. Ручек записи и удаления **нет и не будет**: журнал дописывается
сервисами в той же транзакции, что и само изменение, а ручка «добавить запись»
позволила бы дописать в него что угодно и когда угодно — то есть отменила бы
весь смысл затеи не хуже, чем ручка «удалить» (см. [07-security.md](07-security.md)).

| Метод | Путь | Права | Описание |
|---|---|---|---|
| GET | `/audit` | 🔑 `audit.view` | Журнал. Фильтры: `actor_id`, `entity_type`, `entity_id`, `source`, `action`, `search` (по имени человека и названию объекта), `since`, `until`; `page`/`per_page` (до 100) |

У области `audit` единственное действие — `view`, и журнал можно отдать роли, не
делая человека владельцем системы. `edit` и `delete` не объявлены: запрет на
правку стоит в самой модели, и завести здесь такие права значило бы обещать то,
чего система не позволит никому, включая root. Право, которое ничего не даёт,
хуже его отсутствия.

Запись ответа: `action`, `actor_id`, `actor_name` (снимок), `source`,
`source_ref`, `entity_type`, `entity_id`, `entity_label` (снимок),
`value_before`, `value_after`, `created_at`. `actor_id: null` бывает только у
`source` = `telephony_webhook` и `mail_sync`. `value_before: null` означает «величины
не было», пустая строка — «величина была пустой».

### Ответ встаёт в переписку, а не рядом с ней

`reply_to_id` — id письма, на которое отвечают. Из него берутся заголовки
цепочки (`In-Reply-To`, `References`), а клиент и заявка наследуются, если
своих не назвали: иначе переписка по заявке рвалась бы на первом же ответе —
входящее письмо привязано к клиенту, а ответ на него ни к чему.

**Проверено на двух живых почтовых серверах**, а не рассуждением. В лаборатории
(два независимых maddy, свой DNS, свой удостоверяющий центр) ответ из CRM
приходил собеседнику ОТДЕЛЬНЫМ письмом: почтовые клиенты собирают переписку по
паре `In-Reply-To` + `References`, а транспорт не ставил ни того, ни другого.
Человек получал ответ, не понимая, на что именно.

Одного `In-Reply-To` мало. У ветки длиннее двух писем клиенты смотрят на
`References`, а собрать её неоткуда, кроме как из того письма, на которое
отвечают, — поэтому цепочка сохраняется ПРИ СИНХРОНИЗАЦИИ (`in_reply_to`,
`references` у письма) и уносится в ответ целиком, последними двадцатью
ссылками. У переписки на сотню писем заголовок разросся бы до килобайтов, а
ветку клиенты собирают по последним ссылкам.

Заголовки ставятся **только когда есть на что отвечать**: пустой `In-Reply-To`
хуже отсутствующего — часть клиентов считает его ссылкой в никуда и прячет
письмо из переписки вовсе.

**И только когда есть чем.** В колонке `message_id` лежит ключ идемпотентности,
а не всегда сам заголовок: у письма с Message-ID длиннее 320 знаков (рассылка,
тикет-система) туда кладётся отпечаток `opencrm-sha256:…`. Поставь мы его в
`In-Reply-To` — собеседник получил бы ссылку на письмо, которого у него нет, а
наш внутренний ключ уехал бы в заголовки чужого сервера. Настоящего заголовка у
нас в этом случае нет нигде, и выдумать его нельзя: ответ уходит без цепочки,
как и раньше, но без вранья.

`references` входящего **обрезается хвостом** до тех же двадцати ссылок.
Колонка `TEXT` — это 65 535 БАЙТ, а не символов; письмо из очень длинной ветки
дало бы строку длиннее, MySQL ответил бы `1406 Data too long`, письмо
откатилось бы и не попало в CRM **никогда**: `last_uid` уезжает вперёд по
соседям, и второго захода за ним не будет.

### Заголовок не дописывает чужих заголовков

Тема и адреса уходят в письмо одной строкой: перевод строки внутри значения
дописывает в письмо ЧУЖИЕ заголовки. Тема вида `Счёт\nBcc: vor@example.com`
отправила бы копию постороннему. Библиотека такое отвергает, но отвергает
`ValueError` — он летит мимо `MailTransportError`, и наружу это выходило
пятисотой ошибкой вместо внятного отказа.

### Писать письма может не только владелец

`/mail/accounts` закрыт `settings.manage` и закрыт правильно: там хосты, порты
и логины — настройка уровня фирмы. Но чтобы ОТПРАВИТЬ письмо, всего этого знать
не надо, нужен выбор из двух-трёх адресов, — и для него есть `/mail/senders`,
открытый тому, у кого есть право писать.

Пока этой ручки не было, экраны почты, клиента и заявки спрашивали общий
список. Менеджеру с правом писать он отвечал отказом: ящиков ноль, выбирать не
из чего, кнопки отправки и ответа спрятаны — **письма мог писать только
владелец системы**. Ни типами, ни тестами это не ловилось; нашлось разбором.

### Отказ по части адресатов — не отправка и не провал

`smtplib.send_message` бросает исключение, только когда отвергнуты ВСЕ
адресаты; при частичном отказе он молча возвращает словарь тех, кому не
досталось. Пока этот словарь выбрасывался, письмо на двоих доходило одному, а в
CRM появлялась запись «отправлено» — и узнать об этом было неоткуда. Замерено
на живых серверах именно так.

Теперь письмо **записывается**, а отвергнутые адресаты называются: в ответе
ручки полем `refused`, в ящике — строкой последней ошибки. Бросить отказ здесь
нельзя, и это исправление исправления: к моменту, когда сервер называет
отвергнутых, письмо остальным УЖЕ доставлено. Отказ означал бы, что записи в
CRM нет, — человек нажмёт «отправить» снова, и получившие получат его дважды.
Отозвать письмо нельзя ничем.

### Что делает CRM, чтобы письмо не сочли спамом

Спам решается тремя записями — SPF, DKIM и DMARC, — и **все три живут в DNS
домена, а не в приложении**. Подписывает письмо DKIM'ом почтовый сервер, через
который CRM отправляет (`submission`), а не CRM: у неё нет и не должно быть
закрытого ключа домена. Значит задача приложения здесь ровно одна — не мешать:

- отправлять через SMTP владельца домена, а не напрямую с VPS (так и сделано:
  ящик задаётся настройками, своего MTA у CRM нет);
- ставить корректный `From` — адрес того самого ящика, из которого шлём. Конверт
  (`MAIL FROM`) smtplib берёт из него же, и выравнивание, которого требует
  DMARC, получается само;
- ставить `Message-ID`, `Date`, `MIME-Version` и кодировку — иначе письмо
  выглядит самодельной рассылкой;
- отвечать в цепочку: письмо, вставшее в существующую переписку, у любого
  фильтра весит меньше, чем письмо от того же адреса «ниоткуда».

Измерено в лаборатории: письмо, отправленное CRM через `alpha.test` на
независимый сервер `beta.test`, получило от получателя вердикт
`spf=pass; dkim=pass; dmarc=pass`.

Чего проверить локально нельзя и обещать нечестно: репутацию адреса и сети,
попадание в чёрные списки, поведение конкретных Gmail и Outlook. Это решается
не кодом, а доменом, его историей и настройками у провайдера почты.

Письмо не заводит собственной истории: при появлении оно порождает запись общей ленты (`client_notes`, `kind='email'`, `direction`, `happened_at` = момент отправки письма). Входящее ищет клиента по адресу отправителя; нашли — привязали, не нашли — письмо остаётся непривязанным и **клиента не создаёт**: в ящик фирмы валятся рассылки, спам и ответы роботов, а «клиент» — решение человека.

## Шаблоны сообщений (блок `templates`)

Заготовка на то, что пишут снова и снова: первый ответ на заявку, ссылка на доску, напоминание об оплате. Шаблон — это `name` (уникальное), `body` с подстановками и `channel` (`any` / `email` / `note`) — где он применим. Универсальный шаблон попадает в выдачу по любому каналу: он для того и есть, чтобы один и тот же текст не держать в двух экземплярах.

Весь роутер закрыт `require_module("templates")`. Читать шаблоны может всякий, кто пишет клиентам (`templates.view`), править — тот, кому дано право.

| Метод | Путь | Права | Описание |
|---|---|---|---|
| GET | `/templates/fields` | 🔑 `templates.view` | **Закрытый набор полей**: `{key, needs}`, где `needs` — `""` / `client` / `deal`. Отдаётся с сервера, чтобы список не существовал во втором экземпляре во фронтенде |
| GET | `/templates` | 🔑 `templates.view` | Список по алфавиту. `?channel=email` — годные для письма (включая `any`); незнакомый канал — `422 unknown_channel`, а не пустая выдача, неотличимая от «шаблонов нет» |
| GET | `/templates/{id}` | 🔑 `templates.view` | Один шаблон |
| GET | `/templates/{id}/render` | 🔑 `templates.view` | Готовый текст: `?client_id=`, `?deal_id=` (оба необязательны). Ответ — `{template_id, name, channel, text, missing[], unknown[]}` |
| POST | `/templates` | 🔑 `templates.create` | Завести: `{name, body, channel?}`. Занятое название — `409 template_name_taken` |
| PATCH | `/templates/{id}` | 🔑 `templates.edit` | Изменить любое из трёх полей |
| DELETE | `/templates/{id}` | 🔑 `templates.delete` | Удалить. Уже отправленные сообщения не меняются: применённый шаблон давно стал самостоятельным письмом или записью ленты и связи с шаблоном не хранит |

`render` сделан `GET`'ом намеренно: подстановка ничего не создаёт и не меняет. POST пришлось бы закрывать правом на правку — и смотреть готовый текст смог бы только тот, кому разрешено править сами шаблоны, то есть ровно наоборот тому, ради чего блок заводился.

### Подстановки

Пишутся как `{client_name}`. Всё остальное в фигурных скобках (`{ }`, кусок JSON) — обычный текст: подстановка — это скобки с именем внутри, и отвергать всё подряд значило бы запретить написать скобку, которую имели в виду буквально.

**Набор закрыт и объявлен в коде** (`core/services/template_service.py`). Сейчас в нём шесть полей: `client_name`, `client_company`, `deal_title`, `deal_number`, `board_url`, `company_name`. Открытый набор («любое поле модели») означал бы письмо клиенту с себестоимостью его же заказа, поэтому значения считает поимённый список, а не `getattr` по присланному имени.

Четыре правила, которые важнее самих полей:

- **Неизвестная подстановка не проходит молча.** При сохранении — `422 unknown_placeholder` с перечислением **всех** виноватых (`{clietn_name}`, `{deal_amount}`). Тихая пустота означала бы «Здравствуйте, !» в письме клиенту, и это увидели бы все, кроме автора шаблона.
- **Поле, убранное из набора после того, как шаблон написали**, подставляется видимой пометкой `[?имя]` и попадает в `unknown`. Пустотой оно не становится никогда.
- **Законно пустого значения не бывает «просто пусто».** У клиента может не быть фирмы, у заявки — доски; такое поле подставляется тире (`—`) и называется в `missing`. Прочерк без списка приняли бы за опечатку в шаблоне, список без прочерка не спас бы от «Фирма: » посреди предложения. Слово вместо тире не подставляется намеренно: тело пишут на своём языке, и английская заплатка посреди русского письма хуже честного прочерка.
- **Подставленное не управляет подстановкой.** Значение вставляется буквально (`\1` и `<b>` в имени клиента остаются собой), один проход (клиент по имени «ООО {board_url}» не вытащит чужую ссылку) и в одну строку (имя с переводами строк не дописывает в письмо абзац «P.S. переведите деньги на другой счёт»).

`missing` и `unknown` приходят **всегда**, пустыми списками в том числе: форма ответа не зависит от того, повезло ли с данными, — то же правило, что у выключенных блоков в сводке.

Откуда берутся значения: `deal_number` — это `#{id}` заявки (своего ряда номеров у заявок нет: номер печатают на бланке, а заявку называют словами). `board_url` — **живая** ссылка доски заявки (отозванная и просроченная не годятся: они ведут на страницу с отказом); из нескольких берётся самая ранняя, чтобы ответ не плавал между вызовами. `company_name` — фирма заявки → основная фирма → название бизнеса из настроек. Выключенные блоки `boards` и `companies` в шаблон **не подтекают**: поле становится прочерком, иначе «выключено» означало бы лишь «не видно в меню».

Клиент и заявка обязаны сходиться: заявка чужого клиента — `422 deal_other_client`, тот же код, что у письма и у звонка. Заявка указана, клиент нет — клиент берётся у заявки. Без обоих `render` тоже отвечает: это предпросмотр, где поля про них прочерки.

## Бланки и акты (блок `documents`)

Бланк — это квитанция приёмки: что взяли, у кого, номер и состояние. Акт —
обратная сторона: что сделано и принято. Живут в одном блоке и на одном экране,
потому что это два конца одной работы.

Роутер закрыт `require_module("documents")` целиком, а не по маршруту:
пропущенный маршрут остался бы открытым, и выключенный блок продолжал бы отвечать
тому, кто помнит адрес.

| Метод | Путь | Права | Описание |
|---|---|---|---|
| GET | `/documents` | 🔑 `documents.view` | Список: `search`, `status`, `client_id`, `deal_id`, пагинация |
| POST | `/documents` | 🔑 `documents.create` | Завести бланк |
| GET | `/documents/by-number/{number}` | 🔑 `documents.view` | Поиск сканом: сюда приходит то, что прочитал сканер штрихкода |
| GET | `/documents/{id}` | 🔑 `documents.view` | Бланк + история состояний с именами авторов |
| POST | `/documents/{id}/status` | 🔑 `documents.issue` | Сменить состояние: `{status, note}` |
| GET | `/documents/{id}/print` | 🔑 `documents.view` | **HTML на печать**, а не JSON: две одинаковые половины с линией отреза, штрихкод и QR. `?locale=` переопределяет язык бумаги |
| POST | `/documents/acts` | 🔑 `documents.create` | Завести акт выполненных работ |
| GET | `/documents/acts/{id}` | 🔑 `documents.view` | Акт: позиции и история |
| POST | `/documents/acts/{id}/lines` | 🔑 `documents.edit` | Добавить строку работ |
| DELETE | `/documents/acts/{id}/lines/{line_id}` | 🔑 `documents.edit` | Убрать строку |
| POST | `/documents/acts/{id}/complete` | 🔑 `documents.issue` | Провести акт |
| POST | `/documents/acts/{id}/cancel` | 🔑 `documents.edit` | Отменить непроведённый. Склада и воронки не касается — их не трогали |
| GET | `/documents/acts/{id}/print` | 🔑 `documents.view` | **HTML на печать**: перечень работ, итог и две подписи на одном листе |

**`issue` — не то же самое, что `create`.** Квитанцию печатает приёмщик, а
закрывает работу мастер, и через «видит / не видит раздел» эта просьба не
описывается. Поэтому смена состояния и проведение акта отделены от заведения.

**Проведение акта — один маршрут на три действия**, и это и есть задача: списать
израсходованное, зафиксировать работы, двинуть заявку. Три отдельные ручки
означали бы, что состояние «списано, но заявка не переведена» достижимо обычным
нажатием, а не только сбоем; здесь оно недостижимо вовсе — всё едет одной
транзакцией запроса, и отказ любой части отменяет остальные.

Печать делает браузер, а не сервер: сервер на VPS, принтер на столе. Язык бумаги
переопределяется параметром, потому что бланк печатают под клиента, а не под
сотрудника: приехал турист — печатаем по-английски, интерфейс мастера при этом
остаётся прежним. Себестоимости на бумаге нет и быть не может — клиенту
показывают, во сколько работа обошлась ему.

## Заказы (блок `orders`, по умолчанию выключен, зависит от `documents`)

Запланировано: `POST /deals/{id}/order` и `deal_id` в `PATCH /orders/{id}` — [19](19-sborka-zakaza.md) §6.3.

Заказ — вид бланка, поэтому номер, состояния, печать и поиск сканом живут в
`documents`; здесь только то, чего у квитанции нет: перечень позиций, сборка
сканером, отгрузка и приёмка.

| Метод | Путь | Права | Описание |
|---|---|---|---|
| GET | `/orders` | 🔑 `orders.view` | Список заказов |
| POST | `/orders` | 🔑 `orders.create` | Завести |
| GET | `/orders/{id}` | 🔑 `orders.view` | Заказ с позициями |
| POST | `/orders/{id}/lines` | 🔑 `orders.edit` | Добавить позицию |
| PATCH | `/orders/{id}/lines/{line_id}` | 🔑 `orders.edit` | Изменить позицию |
| DELETE | `/orders/{id}/lines/{line_id}` | 🔑 `orders.edit` | Убрать позицию |
| POST | `/orders/{id}/pick` | 🔑 `orders.edit` | Отметить собранным по отсканированному коду: `{code, quantity_milli}` |
| POST | `/orders/{id}/ready` | 🔑 `orders.edit` | Заказ собран |
| POST | `/orders/{id}/close` | 🔑 `orders.issue` | Провести: отгрузить покупателю или принять от поставщика |
| POST | `/orders/{id}/revert` | 🔑 `orders.issue` | Отменить проведение обратными движениями. Прежние остаются на месте |
| POST | `/orders/{id}/cancel` | 🔑 `orders.edit` | Отменить непроведённый. Резерв снимется сам — он не хранится |
| GET | `/orders/{id}/print` | 🔑 `orders.view` | **HTML на печать**: таблица позиций и итог |

**`edit` против `issue`.** Набирать позиции и двигать склад — разные полномочия:
сборщик набирает, отгружает старший. Поэтому `pick`, `ready` и `cancel` живут на
`edit`, а `close` и `revert` — на `issue`, как выпуск бланка.

Собранное живёт отдельно от заказанного: расхождение «заказано пять, собрано
четыре» видно построчно до отгрузки, а не на выдаче.

`orders.view_amounts` закрывает **закупочную** цену в интерфейсе. В печатной
форме суммы показываются всегда: тот, кто печатает заказ клиенту, обязан видеть
цены — иначе бумага уйдёт с пустым столбцом.

**И закрывает во ВСЕХ ответах, включая ответы кнопок.** Разбор: список и
карточка право спрашивали, а `ready`, `close`, `revert`, `cancel` и заведение
отдавали заказ с суммами всегда — `amounts=True` стояло прямо в вызове
сериализатора. Сборщик без права не видел цен нигде, но стоило ему нажать
«готов», как ответ приходил с итогом и ценами строк. Та же беда, что была у
карточки товара: **`amounts` в сериализаторе по умолчанию `True`, и всякая
ручка, забывшая спросить право, становится обходом.** Стережёт
`tests/test_roles.py`.

**Заказ не закрывается ручкой бланков.** Заказы и бланки живут в ОДНОЙ таблице
(`documents`, разница в `kind`), а `POST /documents/{id}/status` брал запись по
номеру, ни о чём не спрашивая. С правом `documents.issue` заказ переводился в
«выдан»: статус менялся, история перехода писалась, **а склад не двигался
вовсе**. Обход права `orders.issue` — полбеды; хуже второе: остаток остаётся на
месте, товар уезжает, и расхождение всплывает на инвентаризации через месяц,
когда концов уже не найти. Теперь ручки бланков отвечают
`422 document_is_an_order`. Правило стоит на ГРАНИЦЕ, у ручек, а не в общей
смене статуса: `order_service` зовёт её сам и законно.

## Склад (блок `warehouse`, по умолчанию выключен)

Запланировано: артикул выдаётся сам и обязателен, «кто держит товар в брони» в наличии — [19](19-sborka-zakaza.md) §6.2, §6.5.

Роутеров у блока два — `/warehouse` (товары, движения, переезды) и `/warehouses`
(склады как места), — и оба закрыты `require_module("warehouse")`: при
выключенном блоке любой из этих адресов отвечает `403 module_disabled`.

**Остаток не хранится.** Он равен сумме движений и считается запросом, поэтому
колонки «остаток» у товара нет, а `stock_milli` в ответах — всегда результат
агрегата. Количество — целое в тысячных долях единицы (1.25 кг → `1250`), деньги —
целые в минимальных единицах, как везде. У услуги `stock_milli` равен `null`, а
не `0`.

**Снимок отдаётся через приложение, а не статикой.** Тот же довод, что у файлов
клиента: остаток на складе и то, как выглядит деталь, — сведения фирмы, и ссылка
на них не должна работать у всякого, кто её узнал. Медиа досок отдаётся напрямую
nginx, но там это осознанный обмен — витрину показывают клиенту.

Номер товара в адресе снимка обязателен и участвует в отборе: без него номер
снимка от соседней позиции отдавал бы чужую картинку тому, кто его угадал.

Размеров два, оба делаются при загрузке: `view` — длинная сторона до 1600,
`thumb` — до 320. Пропорции сохраняются (в отличие от аватара, где центральный
квадрат безобиден: у детали он отрежет ровно те края, по которым её узнают).
Показывают везде, где место под один, **первый по порядку** — признака «главная»
нет, его завёл бы инвариант «ровно одна». Порядок задаётся целиком
(`PUT …/photos/order`), а не по одному шагу: частичная перестановка требует
знать, что было до неё, и двое, двигающие соседние снимки, получили бы порядок,
которого не задавал ни один.

**Заводить склады — не то же, что двигать товар.** Приход, расход и перемещение
остаются на `create`: кладовщик двигает товар каждый день. А завести,
переименовать или закрыть склад — решение структурное, вроде «завести юрлицо», и
оно на `warehouse.manage`; склады заводят раз в год.

`many` в ответе `/warehouses` считает сервер, а не экран. Правило «выбор склада
появляется, когда складов больше одного» посчитанное на фронте стало бы вторым
экземпляром того же правила, а два экземпляра расходятся молча. По той же причине
раскладка «где и сколько» (`by_warehouse` у товара) приходит только при
нескольких складах: при единственном она повторяла бы общий остаток.

`warehouse_id` в теле движения необязателен — не прислали, попадёт на основной
склад. Пока склад один, форма о нём вообще не спрашивает.

Переезд отдан **отдельным списком**, а не строками в общей истории: там он
читается плохо — две строки подряд с разными знаками, и понять, одно это событие
или два разных, можно только по времени и по памяти. Здесь он одна запись: что,
сколько, откуда, куда и кто.

**Суммы закрыты отдельным правом.** `warehouse.view_amounts` прячет
себестоимость, поэтому один и тот же ответ у двух сотрудников разный. Право
проверяется и в ответах пишущих ручек тоже: умолчание «показывать суммы» в
сериализаторе делало из `PATCH` обход — кладовщик не видел закупочную цену в
списке и в карточке, но получал её в ответ на переименование товара.

Про `POST /warehouse/moves`:

- Расход и списание всегда уменьшают остаток, какой бы знак ни прислали.
- **Уход в минус разрешён** и помечается флагом `went_negative` в ответе: товар
  часто отдают раньше, чем заносят приход, и запрет заставил бы либо не
  записывать расход, либо выдумывать приход. Обе лжи хуже честного минуса.
- `quantity` принимается строкой и разбирается на сервере через `Decimal`.
  Лишние знаки после запятой отвергаются (`422 quantity_too_precise`), а не
  округляются: молчаливое округление и есть причина, по которой одно и то же
  списывают дважды.
- Нулевое количество — `422 zero_quantity`; движение по услуге — `422
  service_has_no_stock`; несуществующая заявка — `404 deal_not_found`.
- Движение не редактируется и не удаляется: ошибку исправляют обратным движением.

**Нехватка перед отгрузкой считается по ТОВАРУ, а не по строке.** У бумаги
(заказа, акта) минус спрашивается подтверждением — `confirm_negative`, — и
подтверждение это единственное, чем «увести склад в минус» отличается от
«увести случайно». Разбор: один товар в бумаге встречается дважды запросто (две
цены, два комментария, два исполнителя), а каждая строка сверялась с остатком
поодиночке. Две строки по 5 при остатке 6 проходили обе — списать предстояло
10. Остаток уходил в минус молча, мимо подтверждения. Теперь строки одного
товара складываются, и в отказе названа ОБЩАЯ потребность: иначе человек сверяет
и не понимает, почему 6 меньше 5.

## Наклейки (блок `labels`, по умолчанию выключен, зависит от `warehouse`)

Штрихкоды товаров, поиск сканером и печать наклеек. **Сканер здесь ничего не
требует от сервера**: он работает как клавиатура — «печатает» цифры в поле и
жмёт Enter, — поэтому со стороны API это обычный запрос с кодом в адресе, без
единого драйвера и разрешения браузера.

| Метод | Путь | Права | Описание |
|---|---|---|---|
| GET | `/labels/products/{id}/barcodes` | 🔑 `labels.view` | Коды товара |
| POST | `/labels/products/{id}/barcodes` | 🔑 `labels.create` | Привязать код: `{code, kind, pack_size_milli, is_primary}` |
| POST | `/labels/products/{id}/barcodes/internal` | 🔑 `labels.create` | Выдать собственный код — тому, у чего заводского нет |
| POST | `/labels/products/{id}/barcodes/{barcode_id}/primary` | 🔑 `labels.create` | Какой код печатать на наклейке |
| DELETE | `/labels/products/{id}/barcodes/{barcode_id}` | 🔑 `labels.delete` | Отвязать код |
| GET | `/labels/scan/{code}` | 🔑 `labels.view` | Товар по отсканированному коду. Не нашли — `404` с самим кодом внутри, чтобы экран сказал «код 20000127 не найден» и предложил завести товар прямо отсюда |
| GET | `/labels/print` | 🔑 `labels.view` | **HTML на печать**: `?product_id=` списком, `copies`, `preview`, `locale`. Пустая пачка — `422 nothing_to_print` |
| GET | `/labels/settings` | 🔑 `labels.view` | Размер наклейки и что на ней печатать |

**Действий у области три, а не четыре.** Смотреть и печатать — одно и то же
(печать это и есть просмотр страницы), а `edit` не нужен: код не правят, его
отвязывают и привязывают заново. Зато привязка отделена от просмотра отдельным
правом: ошибочно привязанный чужой код означает, что сканер молча подставляет не
тот товар, и заметить это можно только на инвентаризации.

`pack_size_milli` — сколько единиц товара в этой упаковке, в тысячных: штука
`1000`, блок из десяти `10000`. Отсканировали коробку — в заказ уходит десять штук.

`preview` существует ради ленты: подбирая размер под свой рулон, на страницу надо
смотреть, а каждая примерка «вслепую» стоит намотанной термобумаги, которая не
переиспользуется.

Настройки наклейки отданы своей ручкой, а не куском общих настроек: общие закрыты
`settings.view`, а размер рулона нужен всякому, кто печатает. Отдаёт она поля
**списком в порядке реестра**, а не словарём флагов: порядок и зона нужны экрану
настроек, чтобы нарисовать переключатели так же, как поля лягут на наклейку.

### Что на наклейке: реестр, а не набор `if`

Состав наклейки — то, что у каждого дела своё: мастерской нужна единица
измерения, магазину цена, складу размер упаковки. Угадать набор один раз нельзя,
и дописывать его придётся ещё не раз, — поэтому поля живут одной записью в
`core/services/barcode_service.POLYA_NAKLEYKI`.

| Поле | Зона | По умолчанию | Что это |
|---|---|---|---|
| `name` | над штрихкодом | вкл | название товара |
| `note` | над штрихкодом | выкл | заметка, обрезанная по месту |
| `sku` | строкой | вкл | артикул |
| `unit` | строкой | выкл | единица измерения; штуки не печатаются — штука подразумевается |
| `pack` | строкой | выкл | сколько единиц стоит за этим кодом (`×10`) |
| `min_stock` | строкой | выкл | порог заказа |
| `price` | строкой | выкл | цена — **только тому, у кого есть `warehouse.view_amounts`** |
| `company` | под цифрами | выкл | название фирмы из настроек бренда |
| `printed_at` | под цифрами | выкл | дата печати |
| `qr` | рядом со штрихкодом | выкл | QR на карточку товара |

Всё, кроме названия и артикула, выключено. Место на наклейке — главный дефицит,
и включать за человека что-то значит испортить ему первую же ленту.

**Добавить поле стоит одной записи в реестре**, двух строк перевода и одной
строки в перечне подписей на экране. Больше нигде: настройка сеется по ключу
`label_show_<поле>`, ручка отдаёт флаг сама, шаблон печатает зону списком.
Забыть любую из трёх нельзя — `tests/test_labels.py` краснеет на каждую, и на
подпись поля, которого больше нет, тоже.

**Суммы на наклейке спрашивают право склада.** Это была дыра: печать закрыта
`labels.view` и о суммах не спрашивала вовсе, а цену клала безусловно — то есть
кладовщик без `warehouse.view_amounts` не видел цену на экране и печатал её на
наклейке. Денежные поля помечены в реестре признаком `dengi`, а не проверкой
внутри каждой функции: забыть проверку в новой значит открыть дыру молча, а
забытый признак виден в самой записи.

**QR ведёт в CRM, а не наружу.** Смысл в том, чтобы стоящий у стеллажа навёл
телефон и увидел карточку — остаток, снимки, цену. Постороннему она не откроет
ничего: там вход. При `base_url` на `localhost` QR не печатается вовсе:
телефон по такой ссылке не попадёт никуда, а нерабочий код человек попробует
трижды и решит, что сломан сканер.

### Картинка ужимается, а не вылезает

Штрихкод и QR печатаются с `viewBox`, и это не украшение. Обе библиотеки ставят
SVG только `width` и `height`; пока картинку показывают как есть, этого хватает,
но стоит задать ей размер стилями — рамка ужимается, а рисунок внутри остаётся
прежним и выходит за неё. Обрезанный штрихкод не читается вовсе.

Найдено живым осмотром на двух сразу. QR на рулоне 58×40 вылезал за правый край
на 3,7 мм. А у штрихкода то же самое оказалось **давним**: шаблон обещает
«ширина — во всю наклейку», а полоски всё это время печатались своей природной
шириной 37,4 мм; на рулоне 30 мм это значило выход за край на 8 мм, то есть на
мелких рулонах наклейка не работала никогда.

Единицы `viewBox` — те же, в каких нарисовано СОДЕРЖИМОЕ: python-barcode пишет
миллиметры, и полоски внутри тоже в миллиметрах, а миллиметр в пользовательских
единицах SVG равен 96/25,4 ≈ 3,78. Рамка прямо в миллиметрах дала бы рисунок
ровно в 3,78 раза крупнее — замерено.

Отдельно: **штрихкод с цифрами не уступает места тексту**. Пока обе половины
наклейки были равноправны, десять включённых полей на рулоне 30×20 выдавливали
цифры под нижний край. Теперь текст сверху ужимается и обрезается, а код с
цифрами стоит нерушимо: без них наклейка не значит ничего.

Проверено живьём на всех ходовых рулонах со всеми включёнными полями: 58×40,
58×30, 40×30 и 30×20 — ничего не выходит за край, цифры на месте.

Выключение блока **самих кодов не трогает**: они лежат при товарах и ждут, пока
блок включат обратно.

открытым, и выключенный блок продолжал бы отдавать деньги фирмы тому, кто помнит

| GET | `/finance/operations` | 🔑 `finance.view` | Операции за период |
| POST | `/finance/operations` | 🔑 `finance.create` | Записать операцию |

| POST | `/finance/rules` | 🔑 `finance.manage` | Завести правило |

| GET | `/finance/deals/{id}/money` | 🔑 `finance.view` | Сколько получено по заявке |
| GET | `/finance/profit` | 🔑 `finance.view` | Доход минус расход за период, с разбивкой по статьям |
| GET | `/finance/budgets` | 🔑 `finance.view` | Планы и факт по ним |
| POST | `/finance/budgets` | 🔑 `finance.manage` | Завести план |
| PATCH | `/finance/budgets/{id}` | 🔑 `finance.manage` | Изменить план |
| DELETE | `/finance/budgets/{id}` | 🔑 `finance.manage` | Убрать план |

**Пустой остаток к оплате означает две разные вещи, и различает их `status`.**
`GET /finance/documents/{id}/money` отдаёт `due: null` в двух случаях: блок
бланков выключен (тогда и `status: null` — суммы нет, сравнивать не с чем) и
бланк отменён (`status: "cancelled"`). У отменённого «сколько ещё с человека
взять» не равно нулю и не равно сумме — **вопрос не задан**; раньше здесь честно
считалось «сумма минус полученное», и у отменённого заказа с возвращёнными
деньгами получалась полная сумма заказа, то есть долг, которого нет. Ноль на его
месте был бы враньём той же природы, только обратным: он читается как
«рассчитались».

То же и с `paid`: у отменённого нет ни «оплачен», ни «не оплачен». Что на самом
деле с деньгами, говорит `received`, и отмена его не трогает — **отмена бумаги и
возврат денег разные действия**, и сделать можно только одно из двух. Экран
заказа этим и пользуется: при непустом `received` у отменённого он показывает «К
возврату», а не «платить нечего».

**Правка статьи частичная.** `PATCH /finance/categories/{id}` принимает любое
подмножество полей — как и правка правила. Незаполненное означает «не меняй».
Направление в теле принимается, но сменить его нельзя: отказ `direction_is_fixed`
внятнее, чем «лишнее поле».

**Операцию не правят и не удаляют — ручек нет и не будет.** Ошибку исправляют
обратной операцией; поправка начисления заводит корректирующую запись на разницу
и той же датой, а исходная остаётся на месте. Поэтому в реестре прав у области
только три действия: `view`, `create`, `manage`. `edit` и `delete` не объявлены —
право, которое ничего не даёт, хуже его отсутствия, тот же довод, что у журнала
действий.

**`view_amounts` здесь нет и быть не может.** У заявок и склада суммы отделены от
раздела, потому что «ведёт заявку, но не видит маржу» — осмысленная просьба.
Финансы это деньги целиком: раздел без сумм — пустая таблица, поэтому `view` и
есть право на деньги.

`manage` — распоряжаться справочником статей и планами: решение структурное,
вроде «завести юрлицо» или «завести склад». Расходы заносят каждый день, а статьи
заводят раз в год.

Ни одна из этих ручек не складывает операции сама: прибыль, факт по бюджету и
деньги бланка приходят из агрегатов репозитория. Колонок `paid_total`, `paid_at`
и `is_paid` в базе нет — все четыре числа рождаются заново на каждый запрос, и
отдельного маршрута «пересчитать» нет и быть не может: пересчитывать нечего.

## Отчёты (блок `reports`)

| Метод | Путь | Права | Описание |
|---|---|---|---|
| GET | `/reports/funnel` | 🔑 `reports.view` | Воронка за период |
| GET | `/reports/funnel.csv` | 🔑 `reports.view` | Она же выгрузкой |
| GET | `/reports/revenue` | 🔑 `reports.view_amounts` | Деньги за период: `received_*` (пришло в кассу) и `won_*` (сумма выигранных заявок), плюс `basis` — чем меряем |
| GET | `/reports/revenue.csv` | 🔑 `reports.view_amounts` | Она же выгрузкой |
| GET | `/reports/sources` | 🔑 `reports.view` | Откуда пришли клиенты. Деньги в нём прячет `reports.view_amounts` |
| GET | `/reports/sources.csv` | 🔑 `reports.view` | Он же выгрузкой |

Период у всех отчётов общий и приходит зависимостью `Period`: `from`, `to`
(даты) и `tz_offset` (минуты из `Date#getTimezoneOffset()`). Датами, а не
готовыми метками времени, чтобы ссылка на выгрузку осталась обычным адресом,
который можно положить в `href` и переслать; границы дня при этом считаются по
местному календарю. Одним классом-зависимостью, а не пятью одинаковыми
аргументами в каждом роуте: разъехавшиеся умолчания у трёх отчётов на одном
экране — это три разных периода под одной подписью. В каждом ответе период и
валюта повторяются: отчёт без подписи периода — просто набор чисел, распечатку
потом не соотнести ни с чем.

**В отчёте о выручке два числа про деньги, и они разные.** `received_*` — сколько
пришло в кассу; по решению владельца («банк один») это и есть выручка, и только
так виден заказ, оплаченный мимо заявки. `won_*` — сумма выигранных заявок:
величина полезная, но деньгами не являющаяся. Чем меряется выручка сейчас,
говорит `basis`: `cash` при включённом блоке «Финансы», `deals` при выключённом —
тогда операций не существует вовсе, и `received_*` приходят **пустыми, а не
нулевыми** («блока нет» и «денег не приходило» — разные ответы). Экран берёт ось
из `basis`, а не из своей карты блоков. Разбор правила — в
[01-overview.md](01-overview.md).

Выгрузка `revenue.csv` следует за этим: колонка «Выручка» переименована в
«Выиграно на сумму», а «Получено» добавлена **последней** — уже сложившиеся у
людей таблицы поверх этой выгрузки не должны поехать столбцами. При выключённой
кассе ячейка пустая, а не «0,00».

**У отчёта о выручке своё право.** Это деньги целиком, а не отчёт, среди прочего
содержащий суммы; прятать в нём числа значило бы отдавать пустую таблицу, честнее
закрыть его тем же правом, что и суммы. С переходом на кассу охват этого права
фактически расширился: под ним теперь и деньги фирмы, а не только суммы заявок. У отчёта по источникам иначе — там без
денег остаётся осмысленная картина, поэтому он открыт по `reports.view`, а суммы
из него вынимаются.

`deals.view_others` решает, ЧЬИ заявки попадают в отчёт, а не только какие
карточки видно на экране. Без этого запрет декоративен: заявок в списке три, а в
отчёте оборот всей фирмы — и узнать его как раз и было целью.

Выгрузка обязана совпадать с экраном: иначе право обходится кнопкой «скачать», а
это самый вероятный обход из всех. Имя файла несёт период — в папке «Загрузки»
через месяц лежит пять выгрузок, и «reports.csv (3)» не отвечает, какая из них за
июль.

Незнакомое значение `direction`/`outcome` — `422`, а не пустая выдача, неотличимая от «звонков нет» |
| GET | `/telephony/calls/{id}` | 🔑 `telephony.view` | Карточка звонка |

Поля звонка: `duration_sec = null` — длительность неизвестна (не то же, что `0`),
`outcome = null` — звонок ещё идёт. `counterparty` — номер собеседника: у входящего это
звонивший, у исходящего — вызываемый.

Формат события вебхука: `call_id` (обязателен), `direction`, `from`, `to`, `started_at`
(ISO 8601, лучше со смещением), `duration`, `outcome`, `recording`, `operator_email`.
Клиента в теле не спрашиваем и не принимаем — он определяется по номеру.

Вебхук **не закрыт блоком**: у АТС нет способа узнать, что владелец выключил телефонию,
и на ошибку она уходит в ретраи. При выключенном блоке запрос принимается (`200`) с телом
`{"status": "ignored", "reason": "module_disabled"}` и ничего не пишет; подпись
проверяется в любом случае.

## Телеграм: переписка с клиентами (блок `telegram`)

Один бот фирмы, общение только один на один. **Клиент обязан начать разговор
сам** — телеграм не позволяет боту написать первым тому, кто его не запускал;
отсюда ручка приглашения со ссылкой и QR-кодом.

| Метод | Путь | Права | Описание |
|---|---|---|---|
| GET | `/telegram/settings` | 🔑 `telegram.manage` | Состояние подключения. Токен НЕ отдаётся — только `token_tail` из четырёх знаков и признаки `configured` / `webhook_secret_set`. Чаты отдаются как есть: секрета в идентификаторе нет |
| PUT | `/telegram/settings` | 🔑 `telegram.manage` | Токен, имя бота, чат утренней сводки (`digest_chat`), чат тревог о сервере (`alerts_chat`), `retention_months` — сколько месяцев хранить переписку (`0` — вечно, и это умолчание; числом, а не строкой). Пустой токен означает «не меняй»: экран настоящего не знает и вернуть не может. `422 bad_bot_token`, `422 bad_chat_id` |
| DELETE | `/telegram/settings` | 🔑 `telegram.manage` | Отключить бота: снимает вебхук у телеграма и стирает токен с секретом. **Переписка остаётся** — отключение про связь, а не про данные |

| GET | `/telegram/invite` | 🔑 `telegram.view` | Ссылка `t.me/имя?start=метка` и QR-код к ней. `?label=` — только буквы, цифры, дефис и подчёркивание (требование телеграма). `422 telegram_username_missing` |

| POST | `/telegram/chats/{id}/deal` | 🔑 `deals.create` | Завести заявку по переписке. Диалог обязан быть привязан к карточке — `422 telegram_chat_not_linked`, заявка без клиента бессмысленна. Пустое название берётся из последнего входящего |

| GET | `/telegram/stream` | 🔑 `telegram.view` | Поток событий (SSE): новые сообщения и смена присутствия. Соединение живёт пять минут, дальше браузер переподключается сам. | POST | `/telegram/webhook` | 🔓 | Обновление от телеграма. Секрет заголовком `X-Telegram-Bot-Api-Secret-Token`; сверка постоянным временем, ограничитель ДО сверки |

**Действий у области три: `view`, `create`, `manage`** — и каждое отсутствующее
отсутствует намеренно. `edit` и `delete` не объявлены: отправленное сообщение не
правят и не удаляют, клиент его уже прочитал, и «исправить» переписку задним
числом значило бы завести способ подделать доказательство; ошиблись — пишут
следом, как в жизни. `view_others` нет, потому что у диалога нет владельца:
закрепление и ответственный отменены, конфликты показываются баннером, люди
договариваются сами — фильтровать такому праву нечего. `manage` — настройки бота:
писать клиентам приходится каждый день, а подключать бота раз и навсегда.

Заведение заявки, напоминания и карточки спрашивают право **на то, что
заводится, а не на телеграм**. Иначе право читать переписку тихо давало бы право
заводить работу и карточки.

Срок хранения переписки — та самая настройка `retention_months`; старое убирает
`core/services/telegram_uborka.py`. Ноль означает «вечно» и стоит по умолчанию:
молчаливая уборка переписки с клиентом хуже разросшейся базы.

Приём отвечает **200 почти всегда**: любой иной ответ телеграм считает
недоставкой и повторяет часами. Отказом отвечаем ровно на неверный секрет.

## Заявки с сайта

| Метод | Путь | Права | Описание |
|---|---|---|---|
| POST | `/public/leads` | 🔓 | Заявка с формы на сайте. Ключ приёма — в заголовке `X-OpenCRM-Intake-Key`. Ответ всегда `202 {"status": "accepted"}` |
| GET | `/leads/settings` | 🔑 `settings.manage` | Состояние приёма. Ключ **не отдаётся**: только `has_intake_key` |
| POST | `/leads/settings/key` | 🔑 `settings.manage` | Новый ключ. Возвращается **один раз**: `201 {"key": "…"}`. Прежний перестаёт работать в ту же секунду |
| DELETE | `/leads/settings/key` | 🔑 `settings.manage` | Закрыть приём: без ключа публичная ручка отвечает как несуществующая |
| PATCH | `/leads/settings/manager` | 🔑 `settings.manage` | Кому достаются заявки. `{"manager_id": null}` — владельцу системы |

Три последние отвечают тем же телом, что и `GET`, — экран не перезапрашивает
состояние после каждого действия.

Состав ответа `GET /leads/settings`:

| Поле | Что значит |
|---|---|
| `has_intake_key` | Задан ли ключ. Ложь — приёма нет вовсе |
| `chosen_id`, `chosen_name` | Кто **выбран** в настройке. `null` — никто |
| `manager_id`, `manager_name` | Кто получит заявку **сейчас** |
| `intake_path`, `intake_header` | Куда и с каким заголовком шлёт сайт |
| `intake_fields`, `honeypot_field` | Состав тела и имя ловушки |

Пара `chosen_*` и `manager_*` расходится ровно в одном случае — назначенного
отключили, и заявки достаются владельцу системы. Отдай ручка только
действующего, экран показывал бы владельца выбранным (враньё про настройку);
только выбранного — умалчивал бы, что заявки уходят не ему. Обе половины вместе
дают экрану сказать это вслух.

`intake_fields` и `honeypot_field` отдаются, потому что по ним экран настроек
рисует готовую команду для того, кто пишет форму на сайте. Набери их разметка
экрана сама — и разъехавшаяся инструкция была бы хуже отсутствующей: по ней
делают форму, форма не работает, виноватым выглядит продукт. Расхождение с телом
запроса ловит `tests/test_leads.py`.

Тело: `name`, `email`, `phone`, `message`, `website`. Обязательного поля как такового
нет, но **почта или телефон нужны хотя бы одно** — иначе `422 contact_required`:
заявка, по которой не с кем связаться, даёт пустую строку в справочнике.

`website` — **ловушка**. В форме поле скрывается стилями: человек его не видит и не
заполняет, бот заполняет всё подряд. Заполненное поле означает, что заявка не
записывается вовсе, а ответ при этом выглядит как успех — скажи мы «отказано»,
подбирающий за десяток попыток вычислил бы лишнее поле и перестал его трогать.

Что происходит с принятой заявкой:

- клиент ищется по присланному адресу (сравнение через `lower()`, целиком — `_` и `%`
  в адресе это знаки, а не шаблон) и по нормализованному номеру (`phone_norm`, то есть
  `067…` находит карточку с `+380 67…`). Нашёлся — заявка цепляется к нему, **второй
  карточки не будет**; известную карточку форма при этом не правит: знание чужого
  номера не должно давать права переписать в ней почту;
- не нашёлся — заводится карточка с меткой `lead` и источником `site` (отдельной
  колонки «статус» в системе нет; метка фильтруется списком клиентов, источник
  считается отчётом по источникам);
- заводится заявка на **первом открытом этапе воронки** — на том, что настроен у
  бизнеса, а не на зашитом;
- ответственный получает напоминание (блок `tasks`; выключен — заявка принимается
  без напоминания). Кто ответственный — настройка `leads_manager_id`; не задана или
  сотрудник отключён — заявки достаются владельцу системы.

Ответ **одинаковый всегда**: ни идентификатора клиента, ни номера заявки, ни слова о
том, завели карточку или узнали своего. Иначе по разнице ответов кто угодно проверял
бы, есть ли такой человек в базе.

Отказы: `401 intake_not_configured` — ключ приёма не задан, приёма нет вовсе (так
выглядит свежая установка); `401 bad_intake_key`; `413 body_too_large` — тело больше
мегабайта, отсекается по `Content-Length` **до чтения**; `422 bad_email`,
`422 email_too_long`, `422 phone_too_long` — адрес и номер не обрезаются, обрезанный
адрес это другой адрес; `429 lead_rate_limited` — слишком часто с одного адреса
(30 за 10 минут, считаются все обращения, а не одни отказы);
`429 lead_intake_flooded` — форма завела больше 60 новых карточек за час.

Повтор той же заявки в течение 5 минут (двойное нажатие, повторная доставка с сайта)
цепляется к уже заведённой работе: ни второй карточки на доске, ни второго напоминания.

**Заявку шлёт сервер сайта, а не страница в браузере.** Ключ, вставленный в HTML,
знает каждый посетитель; и принимается только JSON — тело другого типа проходит мимо
потолка размера. Ключ здесь не подпись: он закрывает ручку от сканеров и даёт способ
отозвать доступ, но не доказывает, что тело не подменили (у формы нет места, где
хранить секрет, — в отличие от АТС). От потока защищают ограничитель и потолки.

Настройки блока (`site_settings`, в общий `GET /settings` не входят): `leads_intake_key`
— сам ключ, `leads_manager_id` — ответственный. Правят их ручки выше, а показывает
экран «Настройки → Заявки с сайта» (`web/frontend/crm/src/screens/LeadsSettings.tsx`):
состояние приёма, создание ключа, выбор ответственного и готовая команда с
подставленным свежим ключом.

Карточка, заведённая формой, получает источник `site` — он же есть в справочнике
источников (`database/models/client.py`), поэтому в карточке и в отчёте виден
названием, а не ключом, и выбирается руками: человек, который посмотрел сайт и
позвонил, пришёл оттуда же, а форму при этом не заполнял.

## Служебные ручки без сессии

Пять адресов внутри `/api/v1`, у которых нет ни сессии, ни права. Каждый закрыт
чем-то другим, и чем именно — важнее самого списка.

| Метод | Путь | Чем закрыт | Описание |
|---|---|---|---|
| GET | `/metrics` | границей сети | Метрики приложения текстом в формате Prometheus. Блоком `monitoring` закрыт тоже — но снаружи его не пускает nginx: `location = /api/v1/metrics { deny all; }` и он же префиксом |
| POST | `/alerts/webhook` | проверкой, что запрос не шёл через nginx | Доставка от Alertmanager: тревоги, зажёгшиеся или погасшие |
| GET | `/alerts/ready` | тем же | Готова ли CRM принимать тревоги. Ответ «нет» — рабочее состояние, а не отказ |
| GET | `/arcade/leaderboard` | ничем — данных фирмы не касается | Таблица результатов змейки со страницы обслуживания |
| POST | `/arcade/scores` | тем же | Записать счёт |

Метрики закрыты в nginx **дважды**: точным совпадением и префиксом с `^~`.
Одного точного мало — проверено запросами по живому nginx:
`//api/v1/metrics`, `/api/v1/./metrics`, `/api/v1/foo/../metrics` и
`/api/v1%2fmetrics` в запрет упираются, а `/api/v1/metrics/` со слэшем на конце
точному совпадению не равен и уходит в приложение. Сегодня это безопасно по
случайности — Starlette отвечает перенаправлением обратно на запрет, — но
`redirect_slashes` это настройка фреймворка, а не наше решение, и молчаливо
поменять её вправе любое обновление зависимостей. Граница сети не должна зависеть
от такой мелочи.

Приём тревог отличается от вебхука телеграма ответами: там повтор вредил (клиент
получил бы своё сообщение дважды), здесь повтор — **способ доставки** тревоги,
которая не ушла, пока телеграм моргал. Поэтому преходящий отказ отдаётся `503`, а
неразбор (не тот JSON, чужое тело) — двухсоткой: повторять то, чего мы не
понимаем, незачем. И это единственная в системе ручка, где **недоступный Redis не
закрывает приём**: ограничитель здесь стоит против потока, а не против подбора, а
цена отказа наивысшая — тревоги не доставлялись бы вообще, включая правило
`RedisDown`, то есть служба молчала бы именно о той поломке, которая её и
заткнула.

Аркада публична целиком: играют посетители сайта, пока он обновляется, и никакого
аккаунта у них нет. Ни одного действия над данными фирмы здесь нет — только своя
таблица результатов.

## Публичные маршруты (витрина, вне /api)

| Метод | Путь | Описание |
|---|---|---|
| GET | `/b/{token}` | Страница витрины. SSR: OG-теги, первые работы, blurhash. Если PIN — форма PIN. Если недоступна — страница «доступ закрыт» (единый вид для отозванной/истёкшей/неопубликованной/несуществующей — не раскрываем причину) |
| POST | `/b/{token}/pin` | Проверка PIN. Успех → подписанная cookie доступа на этот токен (живёт сессию браузера). Перебор ограничен (см. [07-security.md](07-security.md)) |
| GET | `/b/{token}/data` | JSON с работами для гидрации/дозагрузки (те же проверки доступа) |
| GET | `/media/{work_uid}/{filename}` | Файлы работ. **Отдаёт приложение**, nginx только проксирует |
| GET | `/branding/{filename}` | Логотипы и картинка для соцсетей. Их nginx раздаёт с диска (`/srv/storage/branding/`) |
| GET | `/avatars/{filename}` | Аватары сотрудников, так же с диска |
| GET | `/d/{number}` | Состояние заказа по QR с квитанции, без входа в систему |
| GET, HEAD | `/healthz` | Живо ли приложение: `status`, `schema`, `redis`, `maintenance`. На него завязаны проверка здоровья docker и откат обновления |

**Медиа раздаёт приложение, и это правка по безопасности, а не недосмотр.**
Раньше файлы отдавал nginx прямо с диска, и они не закрывались ничем. Проверено
прогоном: клиент один раз открыл витрину и запомнил адреса картинок; после смены
PIN, отзыва ссылки, истечения срока, снятия доски с публикации и даже удаления
ссылки страница отвечала 401/404, а файлы — 200, причём анониму и без PIN.
Витрина закрыта, работы открыты — то есть отзыв ссылки не отзывал ничего.
Сегодня обработчик проверяет блок `boards`, собирает путь через
`media_service.public_file` и спрашивает `share_service.media_is_public` (или
сессию сотрудника); отказ выглядит как «нет такого» — сказать «есть, но не
покажем» значило бы подтвердить, что работа существует. В nginx на этом месте
стоит `proxy_pass`, а не `alias`.

`X-Accel-Redirect` (приложение проверяет, байты отдаёт nginx) был бы быстрее и
**не сделан нарочно**: такой ответ живёт ровно до тех пор, пока внутренний адрес
в конфиге совпадает с заголовком в коде, а файлы nginx примонтированы из чекаута
и меняются в момент `git checkout` — то есть раньше, чем пересоберётся контейнер
приложения. В это окно новое приложение встречает старый конфиг, редирект уходит
в никуда, и на витринах у всех клиентов пропадают картинки. Приём стоит взять,
когда нагрузка потребует, но вместе с проверкой совпадения, а не вместо неё.

`/d/{number}` — **единственный публичный путь, отдающий данные заказа**, и держит
его ограничитель, а не неугадываемость номера. Номера сквозные, потому что тот же
номер напечатан на квитанции и зашит в QR; сделать его неугадываемым, не сменив
бумагу на руках у людей, невозможно. Отличить «нет такого» от «есть, но не
показываем» можно прямо по коду ответа, и обещать обратное нельзя. Значит вопрос
не в том, возможен ли перебор, а сколько он стоит: без ограничения — нисколько,
тысяча запросов подряд отдаёт весь список заказов мастерской. Ограничитель по
адресу (`DOCUMENT_STATUS_MAX_LOOKUPS` в `web/api/deps.py`) поднимает эту цену с
полуминуты до часов и оставляет живому человеку двадцать обращений за десять
минут; считаются **все** обращения, а не одни промахи — перебор с первого номера
идёт по существующим заказам, то есть по удачным ответам. Закрыть полностью можно
было бы ключом в ссылке, и это осознанно не сделано: ключ обесценит все уже
напечатанные квитанции, а решать, менять ли бумагу на руках у клиентов, не
программисту. Выключенный блок `documents` отвечает здесь так же, как
несуществующий номер.

## Пример: создание ссылки

```http
POST /api/v1/boards/12/shares
Content-Type: application/json

{ "expires_at": "2026-08-22T00:00:00Z", "pin": "4821" }
```

```json
{
  "id": 7,
  "board_id": 12,
  "url": "https://studio.example.com/b/xK9fQ2mNpL7vTzR3aW8bYc",
  "token": "xK9fQ2mNpL7vTzR3aW8bYc",
  "is_active": true,
  "expires_at": "2026-08-22T00:00:00Z",
  "has_pin": true,
  "created_by": 3,
  "created_at": "2026-07-22T12:00:00Z",
  "revoked_at": null,
  "views_count": 0,
  "unique_views_count": 0,
  "last_viewed_at": null
}
```

Три последних поля — статистика: она приходит вместе со ссылкой всюду, где
ссылку отдают списком или в карточке доски.
