# 12 — Живые обновления: список работ

Устройство и обоснование решений — в [12-realtime.md](12-realtime.md). Здесь
только работа: шагами, каждый со своей проверкой.

**Правила этого списка.**

- **Порядок обязателен.** После каждой задачи продукт остаётся рабочим и
  разворачиваемым. Ни один шаг не оставляет систему в состоянии «доделаем
  завтра».
- **Задача — один заход.** Код и тесты в одном коммите; правка моделей — вместе
  с миграцией ([CLAUDE.md](../CLAUDE.md), правило номер один).
- **Порядок работы над каждой задачей** — из [CLAUDE.md](../CLAUDE.md), раздел 2:
  код и тесты → поднять в докере версию **до** правки → обновиться на месте →
  сверить базу. Стенд — `wsl-deploy-stand`.
- **Исполнителей может быть несколько.** Этапы 1–6 — сервер, этапы 7–8 —
  клиент; этап 7 начинается только после 4-го. Внутри этапа задачи идут по
  порядку.
- У каждой задачи три поля: **Что сделать**, **Как проверить**, **Чего нельзя
  сломать**. Третье — не украшение: там перечислено то, что уже работает и что
  эта задача способна испортить незаметно.

**Сокращения путей:** `RT = core/realtime/`, `FE = web/frontend/crm/src/`.

## Этап 1. Шина внутри процесса. Снаружи ничего не видно

Цель этапа: намёк рождается, доезжает до подписчика в том же процессе **после
фиксации транзакции** и никуда больше не уходит. Ни маршрута, ни Redis, ни
клиента. Продукт после этапа выглядит и работает точно как до него.

- [ ] **1.1. Завести `RT` с описанием намёка.**
  - *Что сделать:* пакет `core/realtime/` и в нём `message.py`: неизменяемый
    класс намёка (`topic`, `action`, `entity_id`, `scope_key`, `actor_id`,
    `module`) плюс сериализация в одну строку JSON. Шапка модуля объясняет, чем
    это отличается от `core/events.py` и почему живёт рядом, а не внутри.
  - *Как проверить:* `pytest tests/test_realtime.py` — сборка и разбор намёка,
    отказ на попытке положить поле не из списка.
  - *Чего нельзя сломать:* граница базы. В `RT` не должно быть ни `select()`, ни
    `db.execute` — `tests/test_db_boundary.py` обходит `core/` целиком.

- [ ] **1.2. Буфер намёков в сессии + отправка на `after_commit`.**
  - *Что сделать:* `RT/collector.py`. Слушатели `after_commit` и `after_rollback`
    на `SessionLocal`, буфер в `session.info`. Функция `announce(db, ...)`
    кладёт намёк в буфер. Регистрация слушателей — из `core/`, чтобы
    `database/` не узнал про шину (направление `web → core → database`).
  - *Как проверить:* тест — записали в базу и откатились: не отправлено ничего;
    записали и зафиксировали: отправлено ровно один намёк.
  - *Чего нельзя сломать:* фиксацию и откат. Слушатель не имеет права бросать
    исключение: упавшая отправка не должна превращаться в упавший запрос.
    Отдельный тест: подписчик, который падает, не роняет фиксацию.

- [ ] **1.3. Порядок «фиксация → отправка → ответ», сторож.**
  - *Что сделать:* расширить стенд `tests/test_commit_before_response.py`
    третьей записью в летописи — «отправлено».
  - *Как проверить:* `assert letopis.sobytiya == ["фиксация", "отправлено",
    "ответ"]`. Парный тест: обработчик, который пишет и затем отказывает,
    не публикует ничего.
  - *Чего нельзя сломать:* два существующих теста этого файла и
    `tests/test_transaction_boundary.py`. Они помечают друг друга: перенос
    развилки коммита разрешён только вместе с обоими.

- [ ] **1.4. Внутрипроцессная шина и правило её законности.**
  - *Что сделать:* `RT/bus.py` — подписка/отправка внутри процесса. В шапке
    записать, что она законна ровно в одном сочетании: адрес Redis не задан,
    процесс один, окружение не боевое (тот же довод, что у счётчика попыток).
  - *Как проверить:* два подписчика получают намёк в порядке отправки; снятая
    подписка не получает ничего.
  - *Чего нельзя сломать:* ничего внешнего. Но проверить, что подписчиков может
    быть ноль и это не ошибка (как у `core/events.py`).

- [ ] **1.5. Метрики шины.**
  - *Что сделать:* в `web/api/routes/metrics.py` — `_collect_realtime`:
    `opencrm_realtime_published_total`, `opencrm_realtime_dropped_total`,
    `opencrm_realtime_connections`. Рядом с `_collect_ratelimiter`, тем же
    приёмом.
  - *Как проверить:* `GET /api/v1/metrics` содержит три новые строки с `# HELP`
    и `# TYPE`; счётчик публикаций растёт после записи.
  - *Чего нельзя сломать:* `/api/v1/metrics` закрыт от интернета правилом nginx
    (`deny all` точным совпадением и префиксом). Новые метрики не должны
    раскрывать содержимое — только числа.

## Этап 2. Отбор по правам

Цель: чистая функция «кому этот намёк полагается», проверенная свойством. Всё
ещё без маршрута наружу.

- [ ] **2.1. Функция отбора.**
  - *Что сделать:* `RT/access.py` — `delivers(db, user, hint) -> bool`. Три
    вопроса в жёстком порядке: блок включён (`modules_service.is_enabled`) →
    есть право `view` (`permissions_service.has`) → строка видна
    (`permissions_service.deals_scope` и её родня). Ни одного своего запроса.
  - *Как проверить:* примеры на каждую из трёх причин отказа по отдельности.
  - *Чего нельзя сломать:* порядок «блок, потом право» — тот же, что в
    `require_perm`. Перестановка даёт неверную причину отказа, а через год —
    неверный доступ.

- [ ] **2.2. Карта «тема → область прав и способ сужения».**
  - *Что сделать:* таблица в `RT/topics.py`: тема → (`module`, `area`, вид
    сужения). Сужений пока два: «всем, кто видит раздел» и «по ответственному»
    (`deals`).
  - *Как проверить:* тест перебирает все темы и требует, чтобы `area` и `module`
    существовали в `core/permissions.py` и `core/modules.py` — опечатка роняет
    набор, а не открывает тему всем.
  - *Чего нельзя сломать:* правило «выключенный блок не подписан». Тема без
    `module` допустима только для того, что вне блоков.

- [ ] **2.3. Проверка отбора свойством (главная проверка задачи).**
  - *Что сделать:* тест перебирает пары (роль × изменение) и сверяет два
    множества: кому доставлен намёк — и кто видит запись **настоящим `GET`**
    через `TestClient`. Роли берутся из перебора по реестру прав, а не списком
    руками.
  - *Как проверить:* множества совпадают на каждой паре. Обязательные пары:
    менеджер без `deals.view_others` против чужой заявки; сотрудник без
    `warehouse.view` против движения товара; выключенный блок против намёка от
    него.
  - *Чего нельзя сломать:* правую половину нельзя считать той же функцией
    отбора — она сойдётся с ошибкой заодно. Только HTTP.

- [ ] **2.4. Сторож за сторожем.**
  - *Что сделать:* тест, который ломает отбор (подменяет `delivers` на «всегда
    да») и требует, чтобы проверка 2.3 при этом **падала**.
  - *Как проверить:* без починки — красный, с починкой — зелёный.
  - *Чего нельзя сломать:* ничего. Это единственная защита от проверки, которая
    зелена по недосмотру.

## Этап 3. Общая шина: поток Redis

Цель: намёк доходит до соседнего рабочего процесса. Клиента по-прежнему нет.

- [ ] **3.1. Запись в поток.**
  - *Что сделать:* `RT/stream.py` — `XADD` с `MAXLEN ~ N` (число из 0.1), ключ
    под общей приставкой `opencrm:` из `core/redis_client.PREFIX`. Отдельная
    константа TTL/длины с объяснением, откуда взято число.
  - *Как проверить:* через `FakeRedis` (образец — `tests/test_ratelimit_shared.py`):
    запись появилась, `MAXLEN` соблюдён, ключ под приставкой.
  - *Чего нельзя сломать:* память Redis. 64 МБ общие со счётчиками попыток
    входа, политика `allkeys-lru`. Раздутый поток вытесняет счётчики и **молча
    ослабляет защиту от подбора**. Тест на потолок обязателен.

- [ ] **3.2. Чтение потока в каждом процессе.**
  - *Что сделать:* фоновая задача на процесс: `XREAD BLOCK` с последнего номера
    → раздача локальным подписчикам через шину из 1.4. Запуск и остановка — в
    `lifespan` (`web/main.py`).
  - *Как проверить:* тест: положили в `FakeRedis` — подписчик получил.
    Отдельно — что задача останавливается и не держит процесс при выключении.
  - *Чего нельзя сломать:* старт приложения. Ошибка чтения потока не имеет права
    помешать `lifespan` дойти до конца: сайт обязан подниматься при лежащем
    Redis (и он поднимается — `/healthz` про Redis отвечает по факту работы
    ограничителя, живого опроса там нет).

- [ ] **3.3. Выбор шины: Redis есть — Redis, нет — внутрипроцессная.**
  - *Что сделать:* один переключатель в `RT/bus.py`, по `redis_client.configured()`.
  - *Как проверить:* два теста, оба обязательны: с адресом Redis используется
    поток; без адреса — память, и это не считается ошибкой.
  - *Чего нельзя сломать:* набор тестов гоняется **без** внешних служб. Если
    выбор сломан в сторону Redis, весь набор упадёт; если в сторону памяти —
    молча перестанет проверять поток. Нужны оба теста.

- [ ] **3.4. Redis не отвечает: живость выключается, продукт работает.**
  - *Что сделать:* обработка отказа при записи и при чтении. Запись:
    не бросаем — намёк потерян, счётчик `dropped_total` растёт, в журнал не
    чаще раза в 30 секунд (приём из `core/ratelimit._alarm`). Чтение: задача
    ждёт и пробует снова.
  - *Как проверить:* через `BrokenRedis`: запись в базу проходит **целиком**,
    ответ 200, счётчик потерь вырос. Отдельный тест: **на внутрипроцессную шину
    при недоступном Redis не переключаемся** — частичная доставка хуже её
    отсутствия.
  - *Чего нельзя сломать:* правило из `core/ratelimit.py` — там при лежащем
    Redis **отказ**, здесь **тишина**. Разница намеренная (см. §11 документа), и
    менять поведение ограничителя эта задача не имеет права.

## Этап 4. Маршрут потока

Цель: сотрудник может подключиться и получать намёки. Клиента всё ещё нет — на
этом этапе поток проверяется `curl`-ом и тестами.

- [ ] **4.1. Маршрут `GET /api/v1/live`.**
  - *Что сделать:* `web/api/routes/live.py`. `async def` с потоковым ответом,
    `Depends(require_staff)`, заголовки `Content-Type: text/event-stream`,
    `Cache-Control: no-store`, **`X-Accel-Buffering: no`**. Сердцебиение
    комментарием (`: ping`) раз в 20–25 секунд — меньше, чем `proxy_read_timeout
    120s` у nginx. Срок жизни соединения — четверть часа, дальше закрываем и
    клиент переподключается.
  - *Как проверить:* `curl -N` через nginx на стенде: строки идут по мере
    отправки, соединение живёт дольше двух минут; без cookie — 401.
  - *Чего нельзя сломать:* обработчик обязан быть `async` и не звать ничего
    блокирующего в цикле: `uvicorn --workers N` держит соединения в одном цикле
    событий на процесс, и один синхронный вызов затормозит всех.

- [ ] **4.2. Отдача сообщений с отбором на каждое.**
  - *Что сделать:* подписка на шину внутри обработчика; перед каждой отправкой —
    `delivers(db, user, hint)` из 2.1, со **свежей** сессией. Не доставили —
    молчим (не «пустое сообщение»).
  - *Как проверить:* два подключения разных сотрудников, одна правка → намёк
    пришёл только тому, кто видит запись.
  - *Чего нельзя сломать:* права **не кэшируются** ([07-security.md](07-security.md)):
    «право, снятое секунду назад и всё ещё работающее, — дыра». Тест: сняли роль
    у подключённого — следующий намёк ему не приходит.

- [ ] **4.3. Сессия умерла — поток оборвался.**
  - *Что сделать:* проверка живости сессии на каждом сообщении и на
    сердцебиении; нет сессии — закрываем поток.
  - *Как проверить:* вышли из системы (`POST /auth/logout`) при открытом потоке
    → поток закрылся; удалили сотрудника → закрылся.
  - *Чего нельзя сломать:* «доступ прекращается сразу» при удалении аккаунта
    (`ON DELETE CASCADE` на `user_sessions`). Долгоживущее соединение — самый
    удобный способ это правило обойти.

- [ ] **4.4. Правки в чужих тестах-переборах.**
  - *Что сделать:* три правки, все с объяснением в комментарии:
    1. `tests/test_route_guards.py` — маршрут закрыт `require_staff`, а не
       правом; строка в `EXEMPT` с объяснением «поток не отдаёт данных, отбор
       идёт на каждое сообщение»;
    2. `tests/test_modules.py` — адрес `/api/v1/live` в исключении
       `api_get_paths()`: `sweep` зовёт `client.get(path)` на каждом адресе, и
       бесконечный поток остановил бы **весь набор**;
    3. `tests/test_public_surface.py` — убедиться, что маршрут не попал в
       `PUBLIC_ROUTES` (он требует сессии).
  - *Как проверить:* `pytest tests/test_route_guards.py tests/test_modules.py
    tests/test_public_surface.py` — зелено и без зависаний.
  - *Чего нельзя сломать:* исключение из `api_get_paths()` снимает адрес с
    общего перебора, значит его закрытость обязана проверяться отдельно — см.
    4.5. Без 4.5 эта правка тихо открывает адрес.

- [ ] **4.5. Замена снятому перебору.**
  - *Что сделать:* свой тест закрытости `/api/v1/live`: без cookie → 401; с
    cookie до смены временного пароля → 403 `password_change_required`; при
    выключенной живости → `mode: off` и закрытие.
  - *Как проверить:* три утверждения, каждое отдельным тестом.
  - *Чего нельзя сломать:* ничего. Это долг, взятый в 4.4.

## Этап 5. Догон после обрыва

Цель: вернувшийся из туннеля догоняет пропущенное или честно узнаёт, что
догнать нечем.

- [ ] **5.1. Номер сообщения = номер записи потока.**
  - *Что сделать:* поле `id:` в SSE-сообщении заполняется номером записи Redis
    (у внутрипроцессной шины — свой монотонный счётчик того же вида).
  - *Как проверить:* номера строго возрастают; после перезапуска процесса не
    начинаются заново меньшими (иначе браузер посчитает старое новым).
  - *Чего нельзя сломать:* монотонность. Из неё выводится весь догон.

- [ ] **5.2. Догон по `Last-Event-ID`.**
  - *Что сделать:* читаем заголовок при подключении; `XRANGE` от него,
    отправляем пропущенное **с тем же отбором по правам**, затем переходим в
    обычный режим.
  - *Как проверить:* подключились → отключились → три правки → подключились с
    номером → пришло ровно три, в порядке. Без `sleep`: ожидание — чтение из
    очереди с крайним сроком, один помощник на файл.
  - *Чего нельзя сломать:* права спрашиваются **на момент переподключения**, а
    не на момент записи в поток. Тест: за время обрыва право сняли — старые
    сообщения не приходят.

- [ ] **5.3. `resync`: догнать нечем.**
  - *Что сделать:* номера нет в потоке (подрезали `MAXLEN`, вытеснил LRU, Redis
    перезапустился) или номера нет вовсе (первое подключение) → шлём одно
    сообщение `resync`.
  - *Как проверить:* подрезали поток → пришёл `resync`, а не тишина и не
    половина. Первое подключение без заголовка → тоже `resync`.
