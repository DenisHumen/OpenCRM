# 08 — Деплой

Целевая среда: **Ubuntu 24.04 + Docker Compose**. Один сервер, на нём же хранятся файлы работ.

> **На практике всё делает `./opencrm.sh`** — мастер установки при первом запуске, меню дальше
> (порядок команд — в [README](../README.md#деплой-на-сервер-ubuntu-2404)). Этот документ описывает,
> **что** он делает и **почему именно так**: если что-то пошло не по плану, чинить придётся руками,
> и тогда нужно понимать устройство, а не только последовательность нажатий.

## Состав (файлы в репозитории)

```
opencrm.sh                # мастер установки и меню управления (POSIX sh, без зависимостей)
docker/
├── Dockerfile            # этапы: node собирает фронтенд → app (python:3.12-slim + ffmpeg) → tests
├── entrypoint.sh         # страховочная копия SQLite → alembic upgrade head → uvicorn
├── docker-compose.yml    # app (target: app, healthcheck на /healthz) + nginx + certbot
├── .env.example          # переменные компоуза: домен, каталог данных, UID/GID
└── nginx/
    ├── entrypoint.sh     # выбирает конфиг по наличию сертификата, перечитывает его раз в 6 ч
    ├── maintenance/
    │   └── maintenance.html  # что видит посетитель, пока приложения нет
    └── templates/
        ├── http.conf.template   # пока сертификата нет (и для запуска по IP в локальной сети)
        ├── https.conf.template  # 443 + редирект с 80 + HSTS
        └── locations.inc        # общая часть: раздача файлов и proxy_pass в uvicorn
deploy/                   # автообновление сайта; на хосте, вне контейнеров, только stdlib
├── config.py             #   переменные OPENCRM_UPDATE_*
├── github.py             #   голова ветки (условный GET по ETag)
├── journal.py            #   что развёрнуто + история обновлений
├── runner.py             #   запуск команд и HTTP-проверки (подменяются в тестах)
├── notify.py             #   Telegram
├── updater.py            #   сценарий: тесты → бэкап → деплой → health → откат
├── autoupdate.env.example
└── systemd/
    ├── opencrm-autoupdate.service
    ├── opencrm-backup.service   # разовый запуск scripts/backup.sh
    └── opencrm-backup.timer     # ежедневно в 3:30 (+разброс), Persistent
scripts/
├── autoupdate.py         # CLI автообновления: status / check / watch / force-update / enable
├── backup.sh             # ежедневный бэкап: SQLite .backup + tar storage, ротация 7д/4нед
├── restore.sh            # восстановление (текущая БД откладывается в сторону, не затирается)
├── purge_deleted.py      # окончательная очистка мягко удалённого (карантин 30 дней, --dry-run)
├── reset_root.py         # смена email/пароля root, восстановление доступа
└── migrate_to_mysql.py   # перенос данных при переезде на MySQL
```

`Dockerfile` собирается **до этапа `app`** — последний этап в нём, `tests`,
существует ради автообновления (`docker build --target tests` прогоняет pytest и
падает на красных). Поэтому в compose стоит явный `target: app`: без него pytest
и сами тесты уехали бы в боевой образ.

Перед первым запуском заполните `config/.env` по шаблону `config/.env.example`: в `production` приложение остановится, если `OPENCRM_SECRET_KEY` или `OPENCRM_IP_HASH_SALT` пусты (подробности — [07-security.md](07-security.md)).

Когда переедем на MySQL — добавится сервис `mysql` с собственным томом; для приложения изменится только `OPENCRM_DB_URL` (данные переносит `scripts/migrate_to_mysql.py`, порядок описан в [03-database.md](03-database.md)).

## Разделение ответственности nginx / app

| Путь | Кто отвечает |
|---|---|
| `/media/*` | nginx напрямую с тома (кэш-заголовки `immutable`, файлы никогда не меняются — только создаются/удаляются) |
| `/assets/*` (JS/CSS фронтенда) | nginx, из собранного бандла |
| `/api/*`, `/b/*`, всё остальное | proxy_pass → uvicorn |
| Внутренние файлы клиентов | app проверяет сессию → `X-Accel-Redirect` → nginx отдаёт файл |

Лимит тела запроса в nginx = `OPENCRM_MAX_UPLOAD_MB` + запас.

### Адрес приложения nginx перечитывает на каждом запросе

В `locations.inc` стоит `resolver 127.0.0.11` (встроенный DNS Docker) и **переменная** в
`proxy_pass`. Пара обязательна целиком: имя, записанное литералом, nginx резолвит один раз,
при разборе конфига, и запомненный адрес живёт до перезапуска. Обновление же пересоздаёт
контейнер приложения, и адрес в сети compose достаётся ему не тот же самый — если
освободившийся успел занять кто-то другой.

Поймано на стенде: приложение здорово и отвечает напрямую, а сайт отдаёт 502, потому что nginx
стучится по адресу, которого больше нет. Само не чинится — nginx не падает, и
`restart: unless-stopped` его не трогает. Хуже того, health-check автообновления в такой
ситуации краснеет, откат делает ровно то же самое и краснеет тоже: исправное обновление
превращается в лежащий сайт со статусом `broken`. Регрессия — `tests/test_deploy_config.py`.

### Пока приложения нет

Замена контейнера и миграции занимают секунды, но всё это время `proxy_pass` идти некуда.
Вместо nginx'ового «502 Bad Gateway» отдаётся `docker/nginx/maintenance/maintenance.html`:

- код ответа **503** и заголовок `Retry-After` — по ним поисковики держат страницы в индексе,
  а не выбрасывают как сломанные;
- страница ничего не грузит снаружи (ни шрифта, ни картинки, ни скрипта): всё внешнее вело бы
  на тот же лежащий сайт;
- `<meta http-equiv="refresh">` раз в 15 секунд возвращает посетителя на сайт сам;
- `proxy_intercept_errors` **выключен** — собственные 404 и 500 приложения проходят как есть,
  иначе заглушка подменяла бы настоящие ошибки сайта;
- `/.well-known/acme-challenge/` живёт отдельным location с `root`, поэтому продление
  сертификата работает и во время обновления.

### Определение IP клиента за прокси

Реальный IP клиента используется для rate-limit подбора PIN и хэша IP в журнале просмотров.
`X-Forwarded-For` клиент может подделать, поэтому:

- **`OPENCRM_TRUSTED_PROXY_HOPS=1`** (значение из `docker/.env`, по умолчанию 1): за приложением
  один nginx, и реальный адрес — последний элемент `X-Forwarded-For`, дописанный им
  (`$proxy_add_x_forwarded_for`). Левые элементы шлёт клиент — им не верим. Прямой запуск без
  nginx — `0` (заголовок игнорируется). Появился ещё один прокси впереди (Cloudflare,
  балансировщик облака) — `2`, иначе все посетители сольются в пару его адресов: лимит на подбор
  PIN станет общим на всех, а статистика просмотров — бессмысленной.
  Задавать это в `config/.env` бесполезно: `environment` в compose перекрывает `env_file`,
  и строка молча ничего не делала бы.
- **uvicorn с `--no-proxy-headers`** (в `entrypoint.sh`): иначе uvicorn сам перепишет
  `request.client` по `X-Forwarded-For` ещё до приложения, и подделка снова пройдёт.
  Определение IP целиком за приложением (`core client_ip`).
- **`OPENCRM_WORKERS=1`** (по умолчанию). На SQLite другое значение **не работает вовсе**:
  писатель у неё один на всю базу, и второй процесс не поднимется — упадёт на создании схемы
  или посеве умолчаний с `database is locked`. И приложение, и `entrypoint.sh` откажутся
  стартовать с таким сочетанием, назвав причину. Несколько процессов — только после переезда
  на MySQL (`scripts/migrate_to_mysql.py`).
- Вторая причина держать один процесс: rate-limit хранится в памяти процесса. При нескольких
  воркерах порог фактически умножается на их число — до выноса лимитера в БД/Redis держите один воркер.

Без этой связки ротацией `X-Forwarded-For` можно было бы обойти лимит и перебрать PIN доски.

## Где лежит состояние

Всё, что переживает пересоздание контейнеров, лежит **в домашнем каталоге того, кто запускает compose** — не в именованных томах Docker:

```
~/opencrm/
├── data/         SQLite-база (+ копия *.pre-migrate перед каждой миграцией)
├── storage/      медиа досок, файлы клиентов, брендинг, аватары
├── letsencrypt/  сертификаты и приватные ключи
└── acme/         webroot для http-01-проверки
```

Именованные тома лежат в `/var/lib/docker`, их не видно обычными средствами и легко снести вместе с `docker system prune`. Обычные каталоги видно, их забирает `scripts/backup.sh` и просто переносить на другую машину. Путь меняется переменной `OPENCRM_HOME`.

> **UID.** Контейнер приложения работает под `OPENCRM_UID:OPENCRM_GID` (по умолчанию 1000). Это должен быть владелец каталогов выше, иначе первая же миграция упрётся в «permission denied». Свои значения: `id -u`, `id -g`.
>
> **Ключи.** `letsencrypt/` certbot пишет от root, и приватный ключ остаётся с правами `600 root:root` — внутри домашней папки это выглядит непривычно, но так и должно быть: читать его нужно только nginx.

## Развёртывание с нуля

```bash
git clone https://github.com/DenisHumen/OpenCRM.git /opt/OpenCRM
cd /opt/OpenCRM && ./opencrm.sh
```

Мастер ставит Docker, генерирует секреты, подставляет UID:GID, создаёт каталоги, поднимает стек,
выпускает сертификат и включает автообновление. Те же шаги руками:

```bash
cp config/.env.example config/.env   # секреты, домен, root-креды
cp docker/.env.example docker/.env   # домен, OPENCRM_UID/GID (id -u, id -g)
mkdir -p ~/opencrm/data ~/opencrm/storage ~/opencrm/letsencrypt ~/opencrm/acme
docker compose -f docker/docker-compose.yml up -d --build
# entrypoint сам прогоняет alembic upgrade head; root создаётся на первом старте
```

Секреты мастер генерирует **только на пустом месте**: перезапись `OPENCRM_SECRET_KEY` разлогинила бы
всех сотрудников и обесценила бы подписанные cookie PIN-доступа к уже разосланным доскам. Поэтому
повторный `./opencrm.sh install` — безопасная операция «донастроить недостающее», а не «поставить заново».

Обновление вручную: `git pull && docker compose -f docker/docker-compose.yml up -d --build` — миграции применяются на старте автоматически (перед ними entrypoint снимает копию файла SQLite `*.pre-migrate`). Чтобы это происходило само при новом коммите — см. [Автообновление](#автообновление-из-github) ниже.

## HTTPS: выпуск и продление

Курица и яйцо: server-блок на 443 не поднимется без файлов сертификата, а получить их можно только когда nginx уже отвечает на 80. Поэтому конфиг nginx не статичный — его выбирает `nginx/entrypoint.sh`: нет сертификата, поднимаемся на одном 80 и отдаём каталог проверки; появился — включаем 443 и редирект.

```bash
# 1. домен уже указывает A-записью на сервер, стек поднят и отвечает на 80
# 2. выпускаем сертификат (один раз)
docker compose -f docker/docker-compose.yml run --rm certbot certonly \
    --webroot -w /var/www/certbot -d studio.example \
    --email you@studio.example --agree-tos --no-eff-email
# 3. перечитываем конфиг — nginx увидит сертификат и включит HTTPS
docker compose -f docker/docker-compose.yml restart nginx
```

Дальше вмешательство не нужно: контейнер `certbot` дважды в сутки вызывает `certbot renew` (Let's Encrypt обновляет сертификат за 30 дней до истечения), а nginx каждые 6 часов перечитывает конфиг и подхватывает новый файл. Проверка продления ходит на **80**, поэтому `/.well-known/acme-challenge/` в HTTPS-конфиге намеренно оставлен без редиректа.

Локальная сеть без домена: оставьте `OPENCRM_DOMAIN` пустым — стек поднимется по HTTP и будет доступен по IP. Не забудьте `OPENCRM_BASE_URL`, иначе ссылки на доски будут вести на `localhost`.

## Бэкапы и обслуживание

Расписание ставит `opencrm.sh` при установке — таймером systemd
(`opencrm-backup.timer`, ежедневно в 3:30 с разбросом до 20 минут и `Persistent=true`,
чтобы пропущенная из-за выключенного сервера копия снялась при первом запуске), а на машинах
без systemd — заданием cron. Раньше скрипты бэкапа лежали в репозитории, но запускать их было
некому: «резервное копирование настроено» существовало на бумаге, а на диске не было ни одной
копии.

Проверить: `systemctl list-timers opencrm-backup`. Снять расписание:
`systemctl disable --now opencrm-backup.timer`.

Очистку мягко удалённого расписание не трогает — запускайте по необходимости:

```
30 4 * * * docker compose -f /opt/OpenCRM/docker/docker-compose.yml exec -T app python scripts/purge_deleted.py
```

1. `backup.sh`: консистентная копия SQLite (`sqlite3 .backup`) + tar всего `storage/`; ротация 7 ежедневных + 4 еженедельных.
2. Копии лежат в `~/opencrm/data/backups` — **на том же диске, что и база**. Это спасает от испорченной базы и от собственной ошибки, но не от смерти диска и не от потери сервера. Выгрузка наружу — заготовка в скрипте (age + rclone), включить при наличии стораджа.
3. `restore.sh <db> <storage.tar.gz>`: восстанавливает, откладывая текущую БД в `*.before-restore-*`. Перед подменой скрипт стирает `*-wal`/`*-shm`: база работает в `journal_mode=WAL`, и журнал прежней базы SQLite попытался бы доиграть поверх восстановленной. Удобнее звать через меню (`./opencrm.sh restore`) — оно покажет список копий, остановит приложение и поднимет обратно.

   > Внутри контейнера скрипт запускается как `compose run --rm --entrypoint sh app scripts/restore.sh …`.
   > `--entrypoint` здесь обязателен: у образа `ENTRYPOINT` — это `entrypoint.sh`, и `compose run app <команда>`
   > передаёт команду **ему аргументами**, а не вместо него. Без переопределения вместо восстановления
   > поднимается uvicorn, и вызов висит до таймаута. `compose exec` (им сделан `backup.sh`) энтрипойнт не трогает.
4. `purge_deleted.py`: спустя 30 дней карантина безвозвратно удаляет мягко удалённые доски/клиентов вместе с файлами и чистит истёкшие сессии; `--dry-run` показывает план.

## Автообновление из GitHub

Демон на хосте следит за веткой `main` и, когда там появляется новый коммит, сам
пересобирает стек. Код — пакет `deploy/`, запуск — `scripts/autoupdate.py`.

### Почему опрос, а не webhook

Webhook требует публичного эндпоинта, секрета и проверки HMAC-подписи: узнавший
URL иначе задеплоит что угодно. Опрос не открывает наружу ничего — сервер сам
спрашивает GitHub, — и потому одинаково работает и на VPS, и в локальной сети за
NAT. Цена вопроса мала: `Accept: application/vnd.github.sha` возвращает 40 байт,
а `If-None-Match` превращает «ничего не изменилось» в пустой 304, так что опрос
раз в пять минут — 12 запросов в час против анонимного лимита в 60.

### Порядок деплоя

| Шаг | Что делает | Что будет при неудаче |
|---|---|---|
| `preflight` | проверяет, что рабочее дерево чистое | стоп: правку, сделанную руками на сервере, затирать нельзя |
| `fetch` / `checkout` | забирает коммит, встаёт на него (detached HEAD) | стоп, чекаут возвращается назад |
| `tests` | `docker build --target tests` — pytest на **новом** коде | стоп; сайт не тронут, клиенты ничего не заметили |
| `backup` | `sqlite3 .backup` в работающем контейнере | стоп: без копии миграции необратимы |
| `deploy` | `docker compose up -d --build` | откат |
| `health` | `/healthz` со `status: ok` **плюс** smoke-запросы к настоящим страницам | откат |
| `prune` | `docker image prune -f` — прошлый образ остаётся без тега | не важно: деплой уже удался |

Откат — это прошлый коммит, база из снимка и снова health-check. Если и он
красный, статус `broken`: дальше нужен человек, и приходит отдельное уведомление.

Три вещи, которые легко упустить:

- **Бэкап строго до `deploy`.** Миграции накатывает `entrypoint.sh` при старте
  контейнера, и вперёд они необратимы: откат одного лишь кода оставил бы старое
  приложение против новой схемы.
- **Health-check не про контейнер.** «Поднялся» ничего не доказывает: `/healthz`
  ходит в базу, а smoke-запросы (`OPENCRM_UPDATE_SMOKE_URLS`) проверяют, что
  страницы действительно отдаются через nginx.
- **Упавший коммит не пробуется снова.** Он запоминается в `failed_sha`, иначе
  демон пересобирал бы заведомо сломанную версию каждые пять минут и слал бы об
  этом сообщения. Повтор — `force-update` или следующий коммит в ветке.

База возвращается из снимка **только если контейнер успели заменить**. Упади
сборка раньше — старое приложение всё это время обслуживало клиентов, миграции не
запускались, и откат базы стёр бы их работу за время сборки. Такая потеря тиха и
необнаружима, тогда как обратная ошибка (старый код против новой схемы) шумит и
ловится тем же health-check'ом; снимок при этом остаётся лежать на диске.

При восстановлении стираются `*-wal`/`*-shm` (журнал новой версии доиграл бы
поверх), а неудачная база не удаляется, а откладывается в
`opencrm.db.failed-update-*`: в ней данные за время неудавшегося обновления.

### Установка

```bash
cp deploy/autoupdate.env.example ~/opencrm/autoupdate.env   # репозиторий, Telegram, пороги
sudo cp deploy/systemd/opencrm-autoupdate.service /etc/systemd/system/
sudo systemctl enable --now opencrm-autoupdate
journalctl -u opencrm-autoupdate -f
```

Юнит запускается от пользователя, который владеет `~/opencrm` **и самим
чекаутом** `/opt/OpenCRM`, и состоит в группе `docker` — root не нужен. Разойдись
владелец репозитория с этим пользователем, git откажется его трогать («detected
dubious ownership»), и обновление встанет на первом же `git status`.

На Ubuntu 24.04 системный `python3` — это 3.12, а пакету `deploy/` хватает
стандартной библиотеки: ни venv, ни pip для демона не нужны. Docker ставится из
репозитория Docker, а не `apt install docker.io`: в последнем нет плагина
`docker compose` v2. Пошаговая установка — в [README](../README.md#деплой-на-сервер-ubuntu-2404).

> **`OPENCRM_HOME` должен совпадать.** Демон запускает `docker compose` со своим
> окружением из `autoupdate.env`. Если путь там разойдётся с тем, под которым вы
> поднимали стек руками, compose примонтирует другие каталоги — и сайт после
> обновления окажется с пустой базой. Поэтому переменная задана в
> `autoupdate.env.example` явно, а не оставлена на усмотрение `$HOME`: у
> systemd-службы он не обязан совпадать с вашим.

Без systemd годится и cron: `*/5 * * * * cd /opt/OpenCRM && python3 scripts/autoupdate.py check`.

Демон обязан жить **на хосте, а не в контейнере**: он пересобирает контейнеры и
внутри одного из них не пережил бы собственный деплой. Поэтому пакет `deploy/`
не импортирует ни `core`, ни `web`, ни `config` и обходится стандартной
библиотекой — ему нужны только Python, git и docker.

### Команды

```bash
python scripts/autoupdate.py status         # что развёрнуто, есть ли обновление, чем кончилось прошлое
python scripts/autoupdate.py check          # один проход
python scripts/autoupdate.py force-update   # передеплоить сейчас, даже если коммит тот же
python scripts/autoupdate.py history -n 20  # журнал обновлений
python scripts/autoupdate.py disable        # выключить автообновление (перед ручными работами)
python scripts/autoupdate.py enable
```

Состояние — в `~/opencrm/updates/`: `state.json` (что развёрнуто, флаг
автообновления, ETag) и `history.jsonl` (по строке на попытку — коммит, время,
исход, шаги). Разделены потому, что состояние перезаписывается, а история только
дописывается: даже потеряв состояние, видно, что происходило.

Уведомления — Telegram (`OPENCRM_UPDATE_TELEGRAM_TOKEN` и `..._CHAT`). Не задан
токен — обновление работает молча, исход виден в `status`. Сетевые сбои опроса в
историю не пишутся и уведомлений не шлют: при опросе раз в пять минут они
затопили бы журнал.

Те же тесты гоняет GitHub Actions (`.github/workflows/tests.yml`) на push и PR —
чтобы красный коммит был виден сразу, а не через пять минут в уведомлении об
откате.

### Гейт по проверкам GitHub

Деплоится только коммит, у которого проверки в GitHub уже зелёные
(`OPENCRM_UPDATE_REQUIRE_CI=1` по умолчанию). Смотрим оба механизма: check-run'ы
Actions и commit statuses внешних сервисов. Три исхода:

| Проверки | Что делает обновлятор |
|---|---|
| зелёные | едет дальше — preflight, тесты в образе, снимок базы, деплой |
| ещё идут | ждёт (`waiting-checks`) и пробует на следующем опросе; в историю и в Telegram не пишет |
| красные | отказ с записью в историю и уведомлением; коммит запоминается в `failed_sha` |

Разница между «ждём» и «отказ» принципиальна: коммит с недосчитанным CI в
`failed_sha` не попадает — иначе, позеленев, он не поехал бы уже никогда.
По той же причине на ожидании сбрасывается ETag: без этого следующий опрос
получил бы от GitHub 304 «ничего не изменилось» и до проверок бы не дошёл.

`force-update` гейт не проходит — им выкатывают фикс ровно тогда, когда сам CI и
сломан. Выключать `REQUIRE_CI` осмысленно только там, где Actions нет вовсе:
иначе гейт будет ждать проверок, которых никто не запустит.

Локальные тесты в образе (`docker build --target tests`) гейт **не заменяет**: CI
собирает другую машину и другое окружение, и обе проверки ловят разное.

### Почему обновление может не ехать

`status` называет причину прямым текстом. Две из них однажды остановили боевой
сервер наглухо, и обе — про git, а не про код:

- **`detected dubious ownership`** — каталог принадлежит одному пользователю
  (`git clone` под `sudo` оставляет его root), а обновлятор работает от другого.
  git в таком случае не делает ничего. Лечится `chown -R $USER:$USER /opt/OpenCRM`
  при установке; сам обновлятор с версии этого фикса зовёт git с
  `-c safe.directory=<чекаут>` и на владельца больше не смотрит.
- **«в рабочем дереве есть несохранённые правки»** — если в списке только
  `M opencrm.sh` и вы ничего не правили, это бит исполнения: его взводила старая
  инструкция по установке (`chmod +x opencrm.sh`). Битом обновление больше не
  останавливается — проверка чистоты идёт с `core.fileMode=false`, а сам бит
  теперь хранится в репозитории, так что `chmod` не нужен вовсе.

Настоящую правку руками обновление по-прежнему не затирает и честно
останавливается — на то и `OPENCRM_UPDATE_ALLOW_DIRTY`.

## Мониторинг (минимум)

- `GET /healthz` — проверка приложения и доступности БД; внешний uptime-мониторинг (UptimeRobot или аналог) на него.
- Логи — в stdout контейнеров (`docker logs`), ротация средствами Docker (`max-size`).

### Свободное место

Приложение следит за диском само — отдельный cron-скрипт не нужен:

- `GET /api/v1/system/storage` — занято/свободно, размер `storage/`, объём корзины, уровень (`ok` / `warning` / `critical`).
- Данные берутся из `shutil.disk_usage` (POSIX `statvfs`), **прав root не требуется**: поле `free` — это `f_bavail`, то есть место, доступное непривилегированному процессу вроде `www-data`. Работает одинаково на Ubuntu и Fedora, внешних утилит не нужно.
- Сотрудники видят баннер в сайдбаре и карточку «Хранилище» на дашборде; root дополнительно получает раздел «Обслуживание» в настройках сайта с кнопкой очистки корзины.
- При нехватке места загрузка файлов блокируется с ошибкой `disk_full` — это защищает от ситуации, когда диск забивается полностью и повреждается база.

Пороги (в `config/.env`):

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `OPENCRM_DISK_WARNING_PERCENT` | 80 | янтарный баннер «место кончается» |
| `OPENCRM_DISK_CRITICAL_PERCENT` | 90 | красный баннер |
| `OPENCRM_DISK_MIN_FREE_MB` | 1024 | аварийный запас: ниже него загрузка блокируется |

Место освобождается двумя путями: `scripts/purge_deleted.py` по cron (карантин 30 дней) и кнопкой «Очистить корзину» в настройках — обе используют один код (`core/services/maintenance_service.py`).
