# Задачи и замыслы OpenCRM

Здесь лежит **вся несделанная работа**. Один файл, чтобы не искать её по
двадцати трём документам: пришёл, взял верхнюю задачу, сделал.

Документация описывает систему **такой, какая она есть**. Этот файл описывает
то, чего в ней ещё нет. Границу держать строго: как только работа сделана,
задача отсюда **уходит**, а описание переезжает в свой документ.

---

## Как этим пользоваться

**Берёшь одну задачу.** Верхняя в разделе — самая важная. Разделы идут по
убыванию цены: сначала то, что портит работающее, потом большие замыслы, потом
замеры. Две задачи разом брать не надо: правило поштучности записано в
`CLAUDE.md` §2 и оплачено — живая проверка находит то, чего не видно в коде.

**Задача здесь — это указатель, а не задание.** У каждой названо, где лежит
разбор: раздел документа с доводами, решениями владельца и подводными камнями.
Разбор надо прочитать до того, как писать код: почти в каждой задаче уже принято
решение, которое не выводится из здравого смысла.

**Работаешь по `CLAUDE.md`.** Оттуда ничего не отменяется: миграция в том же
коммите, запросы только в `database/`, комментарий длиной в три строки, порядок
проверки «код → старая версия в докере → обновление на месте → сверка базы».

**Закончил — убираешь задачу отсюда.** Не зачёркиваешь, а **удаляешь**: список,
где половина пунктов зачёркнута, читать перестают. И в том же коммите правишь
документ, на который задача ссылалась: там появляется описание сделанного —
устройство, доводы, решения. Проверять по этому файлу «что готово» нельзя, для
этого есть `docs/09-roadmap.md`.

**Задача оказалась ненужной — не удаляй молча.** Перенеси её в
`docs/09-roadmap.md`, в раздел «Решения, к которым не возвращаемся», и запиши
почему. Иначе через полгода её заведут снова, уже без повода.

**Новую задачу сюда пишут только с бедой.** Не «хорошо бы», а «сегодня ломается
вот это». Пункт без беды — это не план, а укор: по такому списку решают, чего
ещё «надо», и решают по несуществующему обязательству.

**Чего сюда не пишут:** мелкие правки, которые быстрее сделать, чем описать;
задачи, придуманные под уже написанный код; и всё, что уже названо решением
владельца в разделе «Решено: не делаем».

## 1. Долги, портящие работающее

Небольшие по объёму, но каждый сегодня чем-то вредит.

### 1.1. Тип файла клиента определяется по расширению

Загруженный файл судится по имени, а не по содержимому: `.jpg` с чем угодно
внутри принимается как картинка. Разбор — `docs/07-security.md`.
Сделано будет тогда, когда тип берётся из первых байтов, а расширение —
только подсказка для имени при скачивании.

### 1.2. Процессные замки множатся при `WORKERS>1`

Третье препятствие к нескольким воркерам (первые два закрыты). Замок, взятый
внутри процесса, не виден соседнему процессу, поэтому `WORKERS` сегодня заперт
на единице. Разбор и два закрытых препятствия — `docs/08-deployment.md`.
Сделано будет тогда, когда замки переедут в общий носитель и `WORKERS>1`
поднимется без двойных выполнений.

### 1.3. Пять находок в `opencrm.sh`

Подтверждены сплошным разбором 27.08.2026, каждая — отдельным опровергающим
проходом.

1. **Пароль администратора уезжает в argv** (`cmd_password`): виден в `ps`
   любому на сервере. Рядом в том же файле дважды сделано правильно
   (`grant_db_exporter`, `monitoring password` — через stdin). Нужен флаг
   `--password-stdin` у `scripts/reset_root.py`. Заодно `ask` не глушит эхо.
2. **`die` внутри команды закрывает пульт целиком** (`tui_vypolnit`), хотя
   комментарий рядом обещает обратное.
3. **Строки шапки не обрезаются по ширине рамки**: в окне 60–71 колонки кадр
   переносится и разъезжается.
4. **Ширина строк считается в байтах, когда локаль не UTF-8** (`wc -m` зависит
   от локали): под `LANG=C` рамка и бегущая строка разъезжаются.
5. То же про разметку живого меню под `LANG=C`.

Правка `.sh` не проходит через докерные ворота — shellcheck отдельная работа CI.

### 1.4. Коды отказов у внешних ручек

В коде их 282, в `docs/04-api.md` названо 82. Скопом переписывать не надо:
большинство самоочевидны (`client_not_found`, `file_too_large`), и это выбор
глубины документа. Но **у ручки, которую зовёт внешний, отказ обязан быть
назван** — иначе вызывающий узнаёт о нём в бою. Мерить так:

```python
kody = set(re.findall(r'code="([a-z0-9_]+)"', tekst_sluzhby))
net = sorted(k for k in kody if k not in pathlib.Path("docs/04-api.md").read_text("utf-8"))
```

Сторожа на этот класс нет намеренно: список исключений вышел бы длиннее самой
проверки.

## 2. Большие замыслы

Каждый — не на один заход. Порядок между ними владельцем не задан.

### 2.1. Живые обновления для всей системы

**46 задач, ~3 недели.** План с разбивкой по шагам — `docs/12-realtime-plan.md`,
устройство — `docs/12-realtime.md`.

Сегодня живой слой написан **только под телеграм**: `core/realtime.py` (шина
событий и присутствие на Redis), `core/redis_client.py`, `core/subscriptions.py`,
`GET /telegram/stream`. Общий механизм для заявок, склада и клиентов не начат.
Имя `core/realtime.py` занято мессенджером — переезд задевает три места ввоза.

Сводка на главной получила **времянку**: перезапрос раз в две минуты и только в
видимой вкладке. Снимается задачей 8.7 — до тех пор времянку не трогать.

Решение владельца 02.09.2026: настройка `realtime_enabled` живёт в реестре
блоков, миграция под неё **не нужна** (задача 9.1 переписана).

### 2.2. Публичное API для сайта магазина

**~31 пункт, 2–3 недели.** Разбор — `docs/16-api-sayta.md` (`API-SAYTA.md` в
корне помечен как отменённый им же).

Порядок из разведки: миграция и модели, ничего не подключая → тип склада →
резерв по складу → ключи → зависимость аутентификации → чтение → снимки →
запись → экран.

Сюда же **седьмой пункт сборки заказа** — `/site/availability`, которого не
существует. Резерв там обязан считать `reserve_service`, а не свой запрос по
заказам.

Решения владельца 02.09.2026: витрина остаётся **без кнопки «купить»**; учёт
брони **по складам отложен** — наивный фильтр вычел бы ноль (склад заказу не
проставляется) и отдал бы чужой товар, поэтому «доступно» подписано общим по
всем складам.

### 2.3. Копия базы через сайт

**~12 пунктов.** Разбор — `docs/15-backup-encryption.md`, решения владельца в §0.

Сегодня копия снимается **только из консоли**: `scripts/backup.sh`,
`scripts/restore.sh`, `scripts/verify_backup.py`. Шифрование готово и проверено
кругом (`tests/test_backup_shifrovanie.py`, `tests/test_vosstanovlenie_kopii.py`);
чего нет — кнопок.

Решения владельца 02.09.2026:

- **просто файл, который скачивают руками** — ни почты, ни облака;
- **база и storage отдельными файлами**, а не одним архивом;
- кнопки в **настройках, на видном месте**;
- **кнопка восстановления нужна** — при том что это самая опасная кнопка в
  системе, и порядок из §6 обязателен.

Самое опасное место — неверный пароль у `openssl enc`, который молча отдаёт
мусор вместо отказа (§4).

**Известная дыра, которую закрывать вместе с этим:** рукописный дампер не умеет
писать двоичные значения. Сегодня двоичных колонок в моделях нет, и проверка это
стережёт; появится `VARBINARY` — предмиграционный снимок станет негодным, и
откатывать обновление будет некуда.

## 3. Замеры, которых не было

### 3.1. Внешний пингер с чужой машины

Внутреннее наблюдение сделано целиком, но `blackbox` стоит на том же сервере,
что и сайт. Упавшая машина не сообщит о себе сама — это единственное, чего
изнутри увидеть нельзя. Отдельной строкой потому, что соблазн засчитать блок
`monitoring` за внешний мониторинг велик, а он им не является.

### 3.2. Формальный прогон Lighthouse

LCP < 1.5 с на mobile, на боевом домене. Архитектурно заложено (SSR, blurhash,
WebP, immutable-кэш), но замера не было ни разу.
